# 技术方案：定时任务支持工作流模版

## 背景

当前定时任务（ScheduledTask）只能触发一种执行形态——基于 LoopConfig 的循环任务（引用 Loop 模版读取实时模版，或使用任务上的 LoopConfig 快照兜底）。

与此并行，仓库已有一套完整的工作流（graph）能力：可视化画布编辑、模版创建/保存/列表、运行时按模版启动并冻结快照、运行进度与回放等，但只能由用户在前端手动点击运行，无法被定时任务自动触发。

痛点：用户希望把编排好的工作流模版交给定时任务按 cron 周期自动跑起来。当前定时能力与工作流能力割裂，工作流无法自动化，用户只能守着界面手点。

## 目标

让定时任务在创建/编辑时可选择"工作流模版"作为执行目标，到点后自动按所引用的工作流模版发起一次运行，语义与用户手动从工作流页面发起运行保持一致。

## 范围

做：
- 定时任务新增一种执行类型：工作流模版，可引用一个已保存的工作流模版，触发时按实时模版发起运行。
- 定时任务模型增加承载"最近一次触发失败原因"的能力，保证触发失败时错误信息可全量呈现给用户。
- 前端定时任务表单支持选择执行类型，并在选择工作流时从已有工作流模版列表中挑选。

不做：
- 不改动 cron 调度核心逻辑（它与执行形态无关）。
- 不为工作流类型保存模版快照；运行时统一以实时工作流模版为准。
- 不改动工作流本身的编辑、运行、回放能力。

## 方案设计

### 执行类型区分

定时任务模型引入"目标类型"概念，区分到点后触发哪种执行形态：

- Loop 类型：维持现状，引用 Loop 模版或使用 LoopConfig 快照。
- 工作流类型：只引用一个工作流模版（按标识保存引用关系），不保存配置快照。

未显式指定类型时按 Loop 处理，保证既有定时任务（含升级前创建、缺少目标类型字段的旧数据）行为不变。

### 字段归属与互斥规则

目标类型决定哪些执行相关字段有效，不同类型的字段相互独立、互不混用：

- Loop 类型：只使用 Loop 模版引用与 LoopConfig，不携带工作流模版引用。
- 工作流类型：只使用工作流模版引用，不使用 LoopConfig 与 Loop 模版引用。
- 创建/编辑时若携带了与目标类型无关的字段，服务层按目标类型只保留有效字段、清理无关字段（而非拒绝请求），保证持久化数据不残留跨类型脏字段；只有目标类型的必填项缺失时（如工作流类型未提供有效模版引用）才拒绝请求。
- 允许编辑时切换目标类型（Loop ⇄ 工作流）：按新类型保留对应字段，原类型独有字段被清空，不再参与后续触发。

### 触发分流

定时任务触发逻辑按目标类型分流：

- Loop 类型：保持现有行为不变。
- 工作流类型：按"先校验、后创建运行任务"的顺序触发——先读取并校验实时模版、解析工作区/工作目录，全部通过后再创建归属于本定时任务的运行任务，最后复用现有"从工作流模版发起运行"的启动路径拉起运行。把校验提前到创建运行任务之前，可让模版缺失/校验不通过/运行上下文无效等失败统一归入阶段一（见"触发失败与错误暴露"），不产生孤立运行记录。该启动路径本身就按模版标识在运行时读取实时模版并冻结快照，故"跟随实时模版"天然成立，无需在定时任务侧另存快照。

工作流类型触发时的运行参数来源约定如下：

- 工作流编排内容：统一以所引用的工作流模版为准（运行时读取实时模版）。
- 运行所在的工作区与工作目录：沿用定时任务自身设置，并与现有"从定时任务发起运行"的解析规则保持一致，区分"未设置→回填"与"无效→失败"两类：
  - 工作区未设置（为空）：回填默认工作区，不算失败。
  - 工作区被删除（已设置但不存在）：回退默认工作区，并清空原工作目录（指向已删除工作区、几乎必然失效），改由默认工作区提供工作目录；仅记告警，不算失败。
  - 工作目录未设置（为空）：回填所属工作区的默认工作目录，不算失败。
  - 工作目录无效（已设置但路径不存在/不是目录/越出工作区边界）：判定运行上下文无效，按阶段一失败。
  - 兜底：回退后的默认工作区仍无法解析（如启动期 ensure-default 失败导致默认工作区缺失）时，同样按阶段一失败，不创建运行任务。
- 用户输入：工作流运行由编排内容自身驱动，定时触发无需补充用户输入。
- 运行归属：生成的运行任务必须记录其所属定时任务标识，否则定时任务完全无法感知运行结果。但建立关联只解决"运行任务知道归属哪个定时任务"，不解决"运行结束时由谁回写状态、释放名额"——后者依赖下文"运行状态回写与并发释放"的桥接通路，而工作流运行的结束不天然走这条通路，必须单独补齐。

cron 调度核心逻辑与存储机制不改；但持久化结构需随模型层增加新字段，并对旧数据缺省值做兼容。

### 运行状态回写与并发释放（关键差异）

这是工作流类型与 Loop 类型最本质的差异，也是不能简单"复用现有回写机制"的原因，必须单独设计。

现状回写链路：定时任务每次触发占用一个并发名额（用于"最大并发数"限制）；名额释放与"回写最近运行状态/最近运行任务标识/运行次数"统一依赖"运行任务进入终态时发出的一次完成通知"。Loop 类型运行结束会发出该通知，因此定时任务能自动感知结果并释放名额。

但工作流类型运行结束**不经过这条通路**：工作流有独立的运行编排与终态落地路径，进入终态时只更新自身运行记录与所绑定运行任务的状态，不触发"完成通知"。若照搬"复用现有回写机制"，会出现两个直接故障：

- 并发名额只增不减：每次触发占名额却永不释放，达到"最大并发数"后永久卡死，后续到点不再触发。
- 状态永远停留"运行中"：终态（成功/失败/停止）、运行次数都不回写，用户在列表/详情看不到最终结果。

因此必须显式补齐一条"工作流运行终态 → 定时任务完成通知"的桥接通路，使带定时任务归属的工作流运行进入终态时，触发与 Loop 类型完成时**语义一致**的回写与名额释放：

- 释放该定时任务占用的并发名额，使"最大并发数"对工作流类型同样有效、不被永久占满。
- 回写最近运行状态为真实终态、更新最近运行任务标识与运行次数，遵循既有并发安全与乱序完成保护（多并发或快速完成时，不让旧运行的终态覆盖更新的运行）。

该桥接只对带定时任务归属的工作流运行生效；用户手动发起、不归属任何定时任务的运行不受影响。

### 触发失败与错误暴露

工作流类型触发时，若引用的模版已删除或校验不通过，不做静默兜底，直接报错并记为失败。失败信息按如下方式落地，保证"错误信息全量暴露给用户"：

- 失败位置：体现在定时任务的"最近一次运行状态"上（记为失败），与 Loop 类型触发失败一致；用户在列表/详情即可看到。
- 完整错误文本：定时任务模型新增一个承载"最近一次触发失败原因"的字段（当前模型只有运行状态枚举，不足以容纳完整错误文本）。该字段保存完整错误信息并展示给用户，成功触发时清空。

按失败发生的时点，触发流程分为三个阶段：

- 阶段一·创建运行任务之前失败（模版标识无法解析、模版已删除、模版校验不通过，或运行上下文无效——"无效"按"触发分流"的边界判断：工作区未设置/被删走回填或回退、不算失败，仅工作目录无效或回退后默认工作区仍无法解析才判失败）：尚未产生任何运行任务，失败只记录在定时任务的最近运行状态与"最近一次触发失败原因"字段上，不留孤立运行记录。
- 阶段二·运行任务已创建、但工作流启动/校验失败：此时已存在归属本定时任务的运行任务，但工作流尚未真正跑起来。约定**不回滚（不删除）该运行任务**，而是直接置为失败终态、把完整错误落到该运行任务，并按"最近运行状态/最近运行任务标识/错误原因"回写定时任务——这样"最近运行任务标识"始终指向一条真实、可点开的运行记录，不会出现悬空标识。由于运行任务已创建却未进入正常运行终态通路，此阶段必须释放本次触发占用的并发名额；但该释放与桥接通路的释放**必须互斥、对一次触发只释放一次**：若置失败终态会触发桥接的终态回调，则不再额外手动释放（否则名额双重释放、计数下溢）；若不经过桥接回调，则必须在此显式释放。
- 阶段三·工作流运行已正常启动后失败：运行已进入工作流自身通路，由桥接统一回写终态、释放名额。这一阶段的完整错误属于"运行级错误"，落在运行记录上即可，定时任务侧只需经桥接把最近运行状态记为失败、保证"最近运行任务标识"指向该运行记录。"最近一次触发失败原因"字段只承载阶段一、阶段二的"触发阶段"失败文本，不重复承载运行级错误，避免前后端对该字段语义产生分歧。因此"全量暴露"对三个阶段都闭环：阶段一、二直接读该字段，阶段三经"最近运行任务标识"进入运行记录查看完整错误（与从工作流页面查看一次运行失败一致）。

#### 手动立即运行与 cron 触发统一失败记录

定时任务既能由 cron 自动触发，也能由用户"立即运行"手动触发。现状两条路径对失败处理不一致：cron 触发失败会回写失败状态与原因，手动触发失败只把错误返回给本次请求、不回写。这导致手动触发工作流失败后，列表/详情看不到，与"错误信息全量暴露"冲突。

本方案要求两条路径走**统一的失败记录逻辑**：无论 cron 还是手动，上述三阶段失败都按同一套规则回写最近运行状态、最近运行任务标识与"最近一次触发失败原因"，并释放名额。手动触发额外把错误同步返回给本次请求，仅为即时呈现，不替代回写。

### 前端交互

定时任务创建/编辑表单增加执行类型选择：

- 选择 Loop 模版时，维持现有交互。
- 选择工作流模版时，从已有工作流模版列表中选择一个，提交时带上类型与所选模版引用。

失败原因展示（对应三个阶段，保证"全量暴露"在前端可执行）：

- 展示位置：在列表/详情已有的"最近运行状态"附近增加失败原因入口（如失败状态可展开/悬浮查看，或在详情区域常驻），不新增独立页面。
- 阶段一、二失败：直接读"最近一次触发失败原因"字段并完整呈现（不截断）；该字段在下一次成功触发后清空，展示随之消失。
- 阶段三（运行级）失败：不读该字段，而是依据"最近运行任务标识"提供进入运行记录的入口（点击跳转），由运行记录页面呈现完整运行级错误。
- 字段为空但"最近运行状态"为失败时，前端按阶段三处理：引导用户经"最近运行任务标识"查看运行记录错误，而非显示"无错误信息"。

需要覆盖的边界状态：

- 编辑回显：正确回显执行类型，并在对应类型下选中已引用的模版（Loop 或工作流）。
- 类型切换：表单内切换执行类型时，清理/禁用另一类型独有字段，避免提交跨类型无效字段。
- 模版列表加载失败：明确提示加载失败（而非静默当作空列表），避免误以为没有可选模版。
- 没有任何工作流模版：给出空状态提示，并阻止以"工作流类型但未选择模版"的无效数据提交。
- 已引用的工作流模版被删除：编辑表单明确提示原引用已失效、引导重新选择，而非静默呈现为未选择。

## 风险

- 工作流模版被删除后，引用它的定时任务会持续触发失败。通过"直接报错 + 记录失败状态 + 全量错误信息"让用户能感知并处理，不做隐藏。
- 工作流运行终态不天然走 Loop 的完成通知通路，若桥接缺失或只覆盖部分失败阶段，会导致名额泄漏（达到"最大并发数"后永久卡死）或状态停留"运行中"。本方案通过显式补齐桥接、并要求三个失败阶段都释放名额来规避；验收需专门覆盖名额释放场景。
- 历史数据、手工删除或异常中断可能留下缺少运行元信息的工作流运行目录。运行列表应把这类目录视为已删除残留并自动清理，避免每次加载列表都重复输出不可读告警；但对元信息损坏、解析失败等真正异常仍保留告警，便于排查数据问题。
- 常规探测行为不应污染告警日志。可预期的缺省文件探测、能力枚举刷新等应以低噪声方式记录，只有真正影响功能或需要用户处理的问题才进入告警日志。

## 可观测性

- 定时任务触发、按类型分流、发起工作流运行等关键节点，统一用项目日志输出（含定时任务标识、目标类型、引用的工作流模版标识、生成的运行/任务标识）。
- 工作流模版缺失或校验失败时，记录完整错误文本，并体现在最近运行状态与"最近一次触发失败原因"字段中。
- 桥接节点（终态回写定时任务、释放名额）输出日志（含定时任务标识、运行任务标识、终态状态），便于排查"状态停留运行中""名额未释放"一类问题。
- 工作流运行列表对缺少运行元信息的残留目录做一次性清理，不把这类可恢复残留作为持续告警；清理失败时输出完整错误，其他不可读情况仍按异常告警。
- 缺省配置文件探测不存在属于正常行为，不作为告警输出；能力探测类日志在常规信息级别只保留摘要，完整枚举信息仅用于调试排障。

## 执行步骤

1. `[已完成]` 模型层：为定时任务增加"目标类型""工作流模版引用""最近一次触发失败原因"三个概念；未指定类型时默认按 Loop 处理；明确目标类型与各执行字段的归属关系；对旧数据缺省值做兼容。
2. `[已完成]` 请求/响应层：创建、更新、查询接口透传"目标类型""工作流模版引用"，查询/响应额外透出"最近一次触发失败原因"。
3. `[已完成]` 服务层：创建/更新时按目标类型做校验与字段归一——工作流类型必须提供有效模版引用，否则拒绝；只保留有效字段、清理无关字段；支持编辑时在 Loop 与工作流之间切换。
4. `[已完成]` 触发层：按目标类型分流。工作流类型按以下子动作顺序执行，并在每个失败点按"触发失败与错误暴露"的阶段约定落地：
   - `[已完成]` 解析并校验目标：读取并校验实时模版，按"触发分流"的边界解析工作区/工作目录（工作区未设置/被删走回填或回退、不算失败；工作目录无效或回退后默认工作区仍无法解析才判失败）；判失败时按阶段一处理。
   - `[已完成]` 创建归属运行任务：创建归属于本定时任务的工作流形态运行任务（记录所属定时任务标识），沿用上一步解析出的工作区/工作目录。
   - `[已完成]` 启动工作流运行：复用现有"从工作流模版发起运行"的启动路径；若启动/校验失败，按阶段二处理（置失败终态、错误落运行任务、回写定时任务、释放名额且与桥接释放互斥只释放一次，不回滚运行任务）。
   - `[已完成]` 记录触发结果：成功时记录最近运行任务标识并清空"最近一次触发失败原因"；失败时按对应阶段写入失败状态与完整错误。
   - `[已完成]` 统一失败记录：保证 cron 与手动"立即运行"走同一套失败记录逻辑，手动路径额外把错误返回给本次请求。
5. `[已完成]` 运行状态回写桥接：补齐"工作流运行终态 → 定时任务完成通知"通路，使带归属的工作流运行进入终态时，触发与 Loop 完成时语义一致的回写与名额释放（释放名额、回写最近运行状态/最近运行任务标识/运行次数，遵循乱序完成保护）；不归属定时任务的运行不受影响。（进度：`services/job.SetGraphRunState` 在 GraphRun 同步 Job 终态时复用现有 `OnJobDone` 通知，进而触发 handler 中已注册的 scheduler `MarkDone`，释放该定时任务并发名额并按既有乱序保护回写状态；pending/running 不触发完成通知，重新进入运行态会清理单 Job 完成去重标记，续跑后仍可再次回写。）

## 验收标准

以下均以手工验证为准，并按项目现有构建/检查命令（如 `make build-all`、前端 build 与 lint）验证不引入回归；按仓库约定，本方案不要求新增单元测试。

- 向后兼容：升级前创建、缺少目标类型字段的旧定时任务，仍按 Loop 类型正常触发。
- Loop 类型不回归：创建、编辑 Loop 类型仍可成功，触发行为与现状一致。
- 工作流类型可触发并回写：到点后自动发起一次工作流运行，结果与手动从工作流页面发起一致；运行记录与该定时任务关联，最近运行状态、最近运行任务标识、运行次数等正确回写。
- 工作区/工作目录继承与回填：未设置工作区按默认回填、未设置工作目录按工作区默认目录回填、被删工作区回退默认（并清空原工作目录改由默认提供），上述情形均能正常发起运行；而工作目录无效或回退后默认工作区仍不可用时，按阶段一失败——不产生运行记录、不占名额，失败原因写入字段。
- 运行终态回写：运行进入终态（成功/失败/停止）后，最近运行状态从"运行中"正确翻转为该终态，不一直停留"运行中"。
- 阶段二失败：运行任务不回滚而是置失败终态、完整错误落该运行任务，定时任务的最近运行状态/最近运行任务标识/失败原因被回写，且本次触发占用的名额被释放（无悬空运行记录、无名额泄漏）；名额对一次触发只释放一次，不因显式释放与桥接释放重叠而下溢。
- 乱序完成保护：在"最大并发数">1 时让多个工作流运行乱序完成（较早触发的晚于较晚触发的结束），最近运行状态与最近运行任务标识以最新一次运行为准，不被旧运行终态覆盖。
- 最大并发数与名额释放：工作流类型的"最大并发数"与 Loop 一致——达上限时新触发被跳过；运行结束后名额被释放，下一次到点能正常再触发，连续多次触发不会把上限永久占满。
- 阶段一失败（模版删除/校验不通过/上下文无效）：直接报错、记为失败、完整错误对用户可见；因未产生运行记录，不占名额，后续到点可继续触发。
- 成功触发清空失败原因：上一次触发失败后，下一次成功触发会清空"最近一次触发失败原因"字段。
- 手动立即运行：可成功触发；手动触发失败时，错误既返回给本次请求，也回写到最近运行状态与"最近一次触发失败原因"，与 cron 触发失败表现一致。
- 运行记录残留清理：若存在缺少运行元信息的工作流运行目录，加载运行列表时会自动清理并跳过；后续重复加载不再因同一目录持续输出不可读告警，且其他损坏或不可读错误仍完整输出。
- 日志信噪比：正常缺省文件探测不会产生告警；能力探测刷新不会在常规信息日志中输出大段枚举内容。
- 工作流类型校验：未提供工作流模版引用时，创建/更新被拒绝并给出明确提示。
- 类型切换持久化：编辑时在 Loop 与工作流之间切换并保存后，持久化结果只保留目标类型的有效字段，无关字段被清理。
- 前端展示与切换：列表/详情正确展示执行类型与所引用模版，编辑时可更换为其他模版；表单可在 Loop 与工作流之间切换，模版列表可正常加载与选择。
- 前端边界：模版列表为空时有空状态且无法提交无效数据；列表加载失败时有明确提示；已删除的被引用模版在编辑表单中有失效提示。
- 前端失败原因展示：阶段一、二失败时列表/详情能在最近运行状态附近完整展示失败原因（不截断）；阶段三失败时能经"最近运行任务标识"进入运行记录查看完整运行级错误；字段为空但状态为失败时引导用户去运行记录查看，而非显示"无错误信息"。
