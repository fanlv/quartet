# Loop 存续期控制：运行 / 暂停期改循环配置 + 优雅停止

## 1. 背景与目标

Loop 是一棵由分组和步骤组成的流程树。任务启动或继续后，执行器会基于当时的流程结构顺序推进，结构在执行期不可变；过去用户想修改后续步骤，只能丢弃任务后重建。

**目标**：让用户在任务存续期间调整后续步骤的行为，分三档能力：

1. **暂停期全量编辑**：Stop 后改任意字段、增删 / 重排节点，Continue 生效。
2. **运行期实时改 prompt**：不停循环，改后续未执行 step 的 prompt，下一个 step 生效。
3. **运行期实时改 model / agent / mode**：不停循环，对后续「会新建 session」的 step 生效。

明确**不做**：运行期增删 / 重排 node（用「Stop → 全量编辑 → Continue」覆盖）。

并附带一个相关能力——**优雅停止**（让当前 step 跑完再停，见 §6）：现有 Stop 是硬停，会打断正在执行的步骤，Continue 后需要重跑该步骤；优雅停止则让当前步骤正常收尾，在干净的步骤边界停下。


## 2. 关键执行机制（设计依据）

- 步骤真正开始前会读取本步骤的 prompt、agent、model 和 mode，因此这些运行参数可以在后续步骤开始前更新。
- 正在执行的步骤已经拿到了自己的执行输入，不能通过修改配置来影响当前这一次执行。
- 运行期变量已经是「保存后、后续步骤读取最新值」的模式，运行期改字段复用同一并发语义。
- 暂停后继续执行本来就会重新读取配置并计算恢复点，因此暂停期全量编辑天然契合现有恢复模型。

## 3. 设计：单一入口，按运行态分流

新增**一个**循环配置更新入口，前端始终提交完整循环配置，后端按任务运行态决定怎么应用：

- **非运行中**：允许全量替换循环配置，并根据新结构校准进度和恢复点（档位 1）。
- **运行中**：先校验流程结构是否保持一致：
  - 结构一致 → 只允许更新后续步骤的 prompt / model / agent / mode（档位 2 / 3）。
  - 结构不一致 → 拒绝保存，并提示「运行中只能修改 prompt / model / agent / mode，结构变更请先停止循环」。

## 4. 后端实现

### 4.1 服务端行为

- 非运行中保存：
  - 保存前先迁移旧配置并校验流程合法性。
  - 当结构未变化（仅改文案、展示名或运行参数）时不重置已有进度，保留已完成结果和提前停止展示数据。
  - 当结构变化时才重算总步数，并判断恢复点、当前路径和历史结果是否仍能对应到同一个步骤；失效的数据会被剔除并重新计算计数。
  - 如果旧恢复点已经失效但仍有可保留的成功结果，恢复点会尽量落到第一个尚未成功完成的步骤，避免继续执行时从头重跑已完成步骤。
  - ⚠️ **已知取舍**：删除 / 重排被记录过结果的 step 会丢弃其历史结果条目（早期工具可接受）。

- 运行中保存：
  - 通过节点身份、节点类型、循环 / 会话语义和子节点顺序判断结构是否一致；只修改可编辑运行参数不会被视为结构变更。
  - 校验时会先按语义默认值归一化空值，避免存量配置因为默认值写法不同而被误判为结构变化。
  - 结构一致时采用「先持久化、再应用到运行中任务」的顺序：落盘失败则本次修改不生效，避免出现「界面报错但运行态已经改变」的不一致状态。

### 4.2 执行链路

- 每个尚未开始的步骤在真正执行前都会读取最新的可编辑运行参数，因此运行中保存会影响后续步骤。
- 结构信息仍来自启动 / 继续时的快照；运行中禁止结构变更，所以执行顺序和恢复路径保持稳定。

### 4.3 约束（运行期）

- 改动只对**尚未开始**的 step 生效；正在执行的 step 改不动。
- model / agent / mode 仅对**会新建会话**的步骤生效；复用已有会话的步骤中途换不了模型 / agent（物理约束）。

### 4.4 接口与错误展示

- 更新入口负责校验请求体、按任务运行态分流，并把运行中结构变更映射成用户可理解的冲突提示。
- 前端统一展示保存失败原因；运行中结构变更会提示用户先停止循环再做全量编辑。

## 5. 前端实现

- **复用现有循环配置面板**：编辑模式下标题改为「编辑循环配置」，保存按钮展示保存状态，并隐藏新建任务才需要的工作区选择。
- **运行中结构锁**：运行中禁用新增、复制、移动、删除节点、修改重复 / 迭代次数、切换会话结构和选择脚本等结构类操作，只保留 prompt / agent / model / mode 编辑。锁生效时还会关闭已打开的结构类弹层，避免另一个 tab 或实时事件把任务切到 running 后，当前页面仍提交结构草稿。
- **入口**：Loop 进度头部新增编辑入口，只读场景不显示。保存失败时在编辑面板内展示具体错误。

## 6. 优雅停止（当前 step 跑完再停）

### 6.1 与硬 Stop 的区别

| | 硬 Stop（现有） | 优雅 Stop（新） |
|---|---|---|
| 触发 | cancel context | 设标志位，不动 context |
| 当前 step | 立刻打断 LLM 调用，不记结果 | 正常跑完、记结果、推进 resume |
| 停在哪 | 当前 step 中途 | 下一个 step 边界 |
| Continue 后 | 重跑被打断的 step | 从下一个 step 干净继续 |
| 终态 | Stopped（保留 resume） | Stopped（保留 resume） |

### 6.2 行为

- 优雅停止只在 **step 间隙**生效：当前 step 跑到自然结束（结果已落、resume 已指向下一个 step）后，循环不再进入下一个 step，直接以 **Stopped** 收尾，resume 保留 → Continue 从下一个 step 干净继续，不重跑。
- 进度条语义：**分母不变**。剩余 step 算「待续」，进度条停在当前完成度（如 3/8），不强制满格 —— 和硬 Stop 一致，符合「还能 Continue」语义；这点和主动结束整个工作流的控制信号不同，后者会把剩余步骤视为跳过并重算分母。
- 标志位是 **best-effort**：若当前 step 卡死（LLM 不返回），优雅停止不会打断它，用户可再点硬 Stop 升级。
- 与硬 Stop 竞争：两者都触发时，硬 Stop 的 context 取消在 step 内优先（当前 step 会被打断）。
- 待停标志在任务启动或继续时清除，避免上一轮的停止请求误停新的一轮；命中后即消费清除。此外硬 Stop 以及任务收尾也兜底清除标志，避免「优雅停止后升级硬停」等不经过步骤边界的路径残留陈旧的待停状态。

### 6.3 实现原则

- 优雅停止请求只对活跃运行中的 Loop 生效；任务已经不活跃时，请求不会留下陈旧待停状态。
- 每个步骤完成、准备进入下一个步骤前检查待停状态；命中后任务进入 Stopped，保留恢复点，不把剩余步骤记作已完成。
- 优雅停止的「待停」状态是运行期临时状态，不落盘；刷新、重连和多端同步都以服务端快照里的待停状态为准。
- 前端把 Stop 拆成「Stop after step」（优雅，主）和「Stop now」（硬，次）两个动作；硬停、完成、失败等终态都会清除本地待停展示。
- 任务进入 running 与运行期停止资源注册对外原子可见，避免出现页面显示可停止但后端尚未准备好停止资源的窗口。

## 7. 验证

1. **后端**：构建和相关自动化测试全绿（含本特性单测）。
2. **前端**：构建和组件测试全绿。
3. **运行期改 prompt**：多 group/step loop 跑起来后改后续 step prompt → 下个 step 的 IterationStarted 用新 prompt。
4. **运行期改 model/agent**：修改会新建会话的后续步骤模型 → 下次执行该步骤时使用新模型。
5. **运行期改结构被拒**：running 时增删 node 保存 → 前端显示后端 409 文案，循环不受影响。
6. **档位 1**：Stop → 增删 / 改 node → Continue → 进度分母正确重算、从合理恢复点继续、被删 step 的结果已清理。
7. **优雅停止**：running 时点「Stop after step」→ 当前 step 跑完后停（Stopped），下个 step 没起跑；Continue 从下个 step 干净继续、不重跑当前 step。
