# Loop Config 面板 UI 重设计 —— 方案

> 所属项目：Quartet Web
> 状态：方案讨论中，尚未实施
> 纯文字描述文档，不含实现代码

---

## 一、背景

Loop Config 是 Quartet 前端用来配置"循环 Job"的核心弹窗，涵盖模板、变量、Flow（Main loop / Group / Step 三层）、每个 Step 的 Prompt/Shell 选择、Session 行为（roundMode）、Agent/Model/Mode 覆写，以及底部的保存 / 导入 / 启动等操作。

当前版本在功能完备度上已经够用，但**视觉密度与信息层级**上积累了若干问题，使得初次使用和复杂嵌套场景下的体验都较差。本文只聚焦 UI/UX 层面的重组，不改动后端协议、Flow 数据模型、Session 语义等底层概念。

---

## 二、现状诊断

对当前单栏纵向布局的主要问题：

1. **信息密度失控**：单个 Step 卡片头部同时承载 "Step 编号 / 类型徽章 / 校验状态 / Repeat / Session" 等 5~6 个属性，视觉焦点分散。
2. **类型信息重复表达**：Step 头部的 "Prompt / Shell" 徽章与卡片内部的 "Prompt / Shell" Tab 表达同一件事。
3. **多层盒中盒**：Main loop 卡片 → Step 卡片 → Tab 区 → Session Agent 区 → Message 区，嵌套 4~5 层边框，局促感强。
4. **层级不清**：
    - "Main loop" 标题过小，不足以承担"整个 Flow 的根容器"的视觉权重；
    - "Iterations" 输入框飘在卡片右上角，与"Main loop"的语义关联被物理切开；
    - 两层 "+ Add Step / + Add Group" 按钮并排出现（group 内一组、root 层一组），用户难以判断"加到哪一层"。
5. **次级信息抢占主视觉**：内置变量（`_current_time` 等）以 chips 形态常驻展开，占据与主输入（Message）同等的视觉份额。
6. **底部操作区权重混乱**：Copy config / Import / Save as template / Cancel / Start Loop 五个按钮样式相近，主操作（Start Loop）不够突出。
7. **空状态表达弱**：Variables 区域"暂无变量"的提示文字偏小，"+ Add" 按钮位置偏远。
8. **校验反馈与分类标签撞样式**："Incomplete" 当前以与 "Prompt" 同款徽章展示，容易被误认为分类标签而非错误提示。

---

## 三、设计目标

1. **显著降低单屏信息密度**：让用户在任何时刻都能迅速找到"我现在应该看哪里"。
2. **让 Flow 的树形结构（Main loop / Group / Step）一眼可辨**。
3. **为主输入（Message / Script）腾出足够空间**，次级配置（Repeat / Session / Agent 等）让位。
4. **操作按钮主次分明**：Start Loop 作为主操作视觉突出；低频操作（导出、导入、保存模板）可收起。
5. **渐进披露**：首次打开看到精简信息，展开后才暴露详细配置。
6. **为后续扩展留余地**：步骤拖拽排序、复制粘贴步骤、条件 Group、并行 Group 等未来能力能自然嵌入。

---

## 四、候选方案

### 方案 A：最小增量 —— 折叠 + 收纳（保留单栏）

**核心思路**：保留现有单栏纵向布局，用折叠与收纳把密度压下去。

- Step 卡片默认**折叠**，仅显示一行摘要：序号、类型、Message 前若干字的预览、Repeat、Session；同一时间最多一个 Step 处于展开态（手风琴模式）。
- Step 头部只保留"编号 + 类型图标 + 校验圆点"，其它属性（Repeat / Session）挪到展开后的"Settings"区。
- 内置变量不再常驻，改为 Message 输入框角落的 "插入变量" 按钮触发 popover，popover 内把"自定义变量 / Shell 变量 / 内置变量"分组展示。
- 移除 Step 头部的 Prompt/Shell 徽章，保留内部的 Segment Control 作为唯一的类型切换入口。
- 原来两层 "+ Add Step / + Add Group" 合并为一个 `+ Add ▾` 菜单，用户在菜单里明确选择"Step / Group"，同时按钮位置贴合所在层级（root 层 vs group 内）。
- 底部操作区重排：主按钮 Start Loop 置于右侧并高亮；Cancel 次之；Copy config / Import / Save as template 收入 `⋯ More` 菜单。

**优点**：改动量最小，保留用户熟悉的阅读路径；短期即可上线。
**缺点**：无法根治"嵌套深时结构看不清"的问题；当 Flow 有多层 Group 时仍会形成长列表。

---

### 方案 B：左右两栏 —— Outline + Detail（推荐）

**核心思路**：顶部放全局元信息，主体分左右两栏，左侧是 Flow 的树形大纲，右侧是当前选中节点的详情编辑区。

- **顶部 Meta Bar（紧凑一行）**：Template 选择器、Variables 数量徽章（点开抽屉编辑）、Reset 按钮。
- **主体左右分栏**：
    - **左栏（约 32%）**：Flow Outline。像文件树一样渲染 Main loop → Group → Step；每个节点前加 "校验状态" 小圆点，悬停行尾显示增/删/拖拽柄。点击任一节点即在右栏打开它的详情。
    - **右栏（约 68%）**：当前选中节点的详情面板。
        - 选中 Step 时：展示 Message（或 Script 选择器）、Repeat、Session、Agent/Model/Mode 等完整字段，Message 输入框有足够空间铺开。
        - 选中 Group 时：展示 Iteration count、Group 标签（可选）、校验信息。
        - 选中 Main loop 时：展示全局 Iteration、Flow 统计（节点数、步骤数、总执行次数预估）。
- **底部操作区**：左侧沿用 "X nodes · Y variables" 的元信息；右侧 Cancel + Start Loop（Start Loop 为主按钮），其它操作进 `⋯ More`。
- **小屏降级**：宽度不足时左栏折叠为抽屉，触发按钮固定在顶部。

**优点**：
1. Flow 树形结构一目了然，嵌套 Group 不再靠缩进去推断；
2. Message 输入框 / Agent 配置有充足空间；
3. 增删改移动（乃至将来拖拽排序、剪切粘贴 Step）的语义都在树上操作，非常自然；
4. 可扩展性最好（为条件 Group、并行 Group 留位置）。

**缺点**：
1. 相比方案 A 改动较大；
2. 需要处理小屏响应式降级。

---

### 方案 C：可视化 Flow Canvas

**核心思路**：像 n8n / Dify 的 Workflow 一样，把 Flow 画成可视化节点图：Main loop 是外框，Step / Group 是图中节点，可拖拽、可连线；点击节点在右侧抽屉编辑详情。

**优点**：复杂流程的空间关系最直观；如果未来 Flow 要支持分支、并行、条件，canvas 几乎是唯一优雅的表达方式。
**缺点**：
1. 开发成本最高；
2. 对当前主流用例（线性 1~3 个 Step、偶尔嵌套一层 Group）有过度设计之嫌；
3. 新用户学习成本高于树形大纲。

---

## 五、推荐方案

**推荐方案 B（Outline + Detail 两栏）**，理由：

1. 当前最核心的问题是"层级不清 + 密度过高"，方案 A 只能缓解密度，层级问题仍在；
2. Outline + Detail 是用户熟悉的心智模型（IDE、文件浏览器、Xcode Project Navigator 等），学习成本低；
3. 为未来扩展（拖拽、复制步骤、条件/并行 Group）预留了清晰的操作入口；
4. 相比方案 C 的 canvas，改造成本可控且信息密度最友好。

**若希望分阶段落地**，建议：

- **阶段 1（轻改）**：先落方案 A 中的三个独立改进 —— Step 折叠 + 变量 popover + 底部按钮分主次。短期立即缓解视觉拥挤。
- **阶段 2（重构）**：在阶段 1 的基础上切换到方案 B 的两栏结构，把 Outline 抽出来作为左栏。

---

## 六、通用细节修正（不论选哪个方案都建议做）

以下调整相互独立，可随任一方案一起推进：

1. **类型表达去重**：Prompt / Shell 只保留一处（推荐保留 Segment Control），删除 Step 头部的类型徽章。
2. **校验反馈脱离分类徽章样式**：用红/绿小圆点表达校验状态，鼠标悬停显示错误原因（或在展开后直接在字段下方显示错误文案）；避免与"分类标签"撞样式。
3. **Iterations 输入框贴近 "Main loop" 标题**：让数值与概念在空间上相邻，而不是飘在卡片右上角。
4. **内置变量收纳为 popover**：Message 输入框附近加 `{{}}` 按钮触发，popover 内分组展示"自定义变量 / Shell 变量 / 内置变量"；既节省纵向空间，也让三类变量的心智模型统一。
5. **底部按钮主次分明**：Start Loop 作为唯一主按钮，Cancel 次之；Copy config / Import / Save as template / Update template 收入 `⋯ More` 菜单。
6. **Variables 空状态**：将说明和 Add 按钮并排居中放置，而不是说明文字靠左、按钮靠右。
7. **Add 操作合并**："+ Add Step" 与 "+ Add Group" 合并为一个 `+ Add ▾` 菜单，让"加到哪一层"与"加什么类型"两个选择分离。
8. **节点操作入口收敛**：增/删/复制/移动集中在节点自身的行尾悬浮操作区，而不是分散在多个按钮上。

## 七、风险与权衡

1. **学习成本**：现有用户已习惯单栏布局，切换到两栏后需要短期适应；可通过顶部保留 Template/Variables 的传统位置、以及保留 "Add Step" 语义等方式降低学习陡峭度。
2. **小屏 / 窄窗**：两栏结构在窄窗下必须降级；左栏抽屉化是成熟方案，但需要单独设计抽屉触发按钮和切换动画，开发量不可忽略。
3. **分阶段上线的过渡态**：若采用阶段 1 + 阶段 2 的分步策略，阶段 1 落完后的单栏折叠版是"中间态"，需要避免在此停留过久，以免用户形成新的路径依赖、再迁移到方案 B 时反而感觉违和。
4. **可视化 canvas 方向的放弃**：选 B 意味着短期不做 canvas；未来若 Flow 要支持复杂的分支 / 并行，可能仍需 canvas 化。届时左栏 Outline 与 canvas 可作为同一数据的两种视图并存。

---

## 八、不做的事

- 不改 Flow 数据模型（FlowNode / RoundMode / 校验规则保持不变）；
- 不改后端协议 / 事件；
- 不改 Template 的存储方式与导入导出 JSON 的格式；
- 不引入第三方重量级 UI 库（如 react-flow / xyflow），canvas 方向是远期选项。

---

## 九、后续待确认项

1. 阶段 1 / 阶段 2 的取舍：是一次性做到方案 B，还是先做阶段 1 观察反馈？
2. 左栏 Outline 的节点操作，首版是否包含拖拽排序？（包含会显著抬高工作量，但体验收益明显。）
3. "Main loop" 是否允许未来扩展为多个并列根节点？若允许，Outline 的根节点需预留"可增加"的入口；若不允许，则 Main loop 可作为固定的大纲标题。
4. 变量 popover 的分组顺序与默认展开项（自定义变量优先 vs 内置变量优先），需要与产品口径对齐。
