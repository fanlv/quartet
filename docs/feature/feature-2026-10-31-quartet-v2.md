# Quartet v2.0 整体重构技术方案

## 目标

重构整个项目的交互方式，使 Quartet 的整体体验更接近 Personal Agent（个人智能助手）。

## 概念约定

- **Agent 是业务角色**：指用户对话和 @ 的对象，拥有稳定身份、名称和独立的 SystemPrompt，包括主 Agent 和从 Agent。
- **Harness Client 是执行后端**：指通过 ACP 接入的 Codex、Claude Code、eino-cli 等执行工具，负责实际运行、工具调用和上下文处理。文档不再用“ACP Agent”称呼这类工具。
- **模型属于 Harness Client 的运行配置**：先确定业务 Agent，再选择其本次对话使用的 Harness Client，以及该后端支持的模型、模式和思考级别。

## 功能

- **首页改版**：iOS 和 Web 首页统一采用**群聊式对话界面**，同一群聊中可以有不同的 Agent。用户可以在对话框中 **@ 任意 Agent**，与指定 Agent 对话；**未 @ Agent 时，默认与主 Agent 对话**。
- **IM 接入首页群聊**：现有 IM 消息**统一进入当前首页群聊**，与 Web、iOS 共用消息历史、任务和 Session 管理，普通消息**默认交给主 Agent**。首页标明来源平台、会话和发送者，相关回复及后台任务结果**按原消息来源回传**。
- **首页消息展示**：iOS 和 Web 首页在普通模式下主要展示 Agent 的**回复正文（assistant content message）**。**思考过程和工具调用**放在对应回复正文下方，**默认折叠**，用户可展开查看或收起。
- **首页消息显示模式**：设置中提供**普通模式和调试模式**，默认使用普通模式。**普通模式不显示 `<system-reminder>` 标签及其内部内容；调试模式显示包含该标签及内部内容的完整消息**，便于检查实际投递内容。显示模式持久化保存，仅影响首页展示。
- **Agent 与 Session**：系统**默认提供主 Agent 及默认配置，用户无需先行配置主 Agent**。每个 Agent 可按需配置**独立的 SystemPrompt**，通过 `<system-reminder>` 标签嵌入对话上下文，供 Agent 使用；iOS 和 Web 对话界面在**普通模式下隐藏该标签及其内部消息，调试模式下完整展示**。不同 Agent 分别对应各自**独立的 Session**，同一 Agent 可先后使用多个 Session。
- **对话框选择 Harness Client**：与业务 Agent 对话时，可在 Web、iOS 输入框中**选择底层 Harness Client**，例如 Codex 或 Claude Code，并选择其支持的模型和运行参数。**@ 决定和哪个业务 Agent 对话，Harness Client 决定由哪个执行后端运行**；同一业务 Agent **切换 Harness Client 后，后续消息必须使用新的 Session**，业务身份和任务保持不变。
- **忙碌时的消息排队**：主 Agent 正在处理消息时，用户正常发送的新消息**默认进入当前 Session 的队列**，本轮结束后依次处理。排队消息显示**“等待处理”**，支持在开始处理前撤回；尚未被 Agent 读取时，不显示为已处理。
- **独立任务与会话归属**：用户可显式选择**“开启独立任务”**，为主 Agent 创建新的 Session 并行处理，**原任务继续执行**。每个独立任务展示简短名称，用户通过**“回复该任务”**继续对应 Session；普通发送继续进入主对话。
- **停止并发送**：用户可选择**“停止并发送”**，停止当前执行，**确认停止后在原 Session 中处理新消息**。
- **多 Agent 编排**：群聊中设置一个主 Agent，负责多 Agent 的任务编排，可将任务**分配给一个或多个从 Agent 执行**。耗时任务由从 Agent 后台执行，主 Agent 完成派发后结束本轮交互，**继续接收用户消息**；任务完成后，将结果返回群聊。
- **iOS 语音输入**：支持在群聊中通过语音输入消息，**语音识别为文字后直接作为文本消息发送**。
- **Session 自动管理**：用户与 Agent 对话时，系统**自动判断是复用该 Agent 上一个 Session，还是新建 Session**。**Harness Client 发生切换时必须新建 Session，不受空闲阈值限制**；后端未变时，空闲阈值**默认 30 分钟，允许配置**，从最后一次执行结束与待处理队列清空两者中较晚的时刻开始计时，超过阈值后在下一次发送时新建，否则复用原 Session。**执行、排队及等待用户确认期间不因超时轮换**。
- **历史 Session 感知与检索**：所有 Agent（包括主 Agent 和从 Agent）共享 **v2.0 Session 历史**的查询能力，按**“会话概览 → 搜索相关片段 → 按需读取原文”**的方式了解和使用历史。Agent 可根据当前对话或任务需要主动检索，范围**包含用户与其他 Agent 的历史 Session**，不限于当前 Agent 自己的会话。
- **Session 会话卡片**：每个 Session 自动维护时间、所属业务 Agent、实际 Harness Client、聊天主题、简短摘要、**用户确认的决定和未完成事项**，并记录**摘要覆盖到哪条消息**。每轮交互完成后，后台**复用标题生成所选 Harness Client，通过独立 Session** 增量更新卡片。
- **历史概览注入**：新建 Session 时，通过 **`<system-reminder>` 注入近期会话概览、未完成任务和检索方法**，概览有长度限制，更早的历史通过查询获取；注入内容在**普通模式下隐藏，调试模式下完整展示**。
- **统一历史查询能力**：所有 Agent 通过 **quartet-cli 配合共享 Skill** 使用三项能力：**列出会话**支持按时间、Agent 分页查看会话卡片；**搜索历史**覆盖标题、摘要和聊天正文，返回命中片段、时间、Session 和消息标识；**读取原文**支持围绕命中消息读取前后对话，并继续分页。
- **历史检索范围与核实**：默认搜索**用户消息和 Agent 回复正文**，工具结果按需查询。**摘要用于导航，重要结论回原文核对**，保留对应 Session 和消息标识以便追溯。
- **历史目录与检索索引维护**：由后端统一维护，所有 Agent 共用。首版支持**中文关键词、短语和时间筛选**，后续根据实际检索效果补充语义检索。摘要或索引更新滞后时，**仍可检索最新原文，并明确说明结果是否完整**。
- **移除 Workspace 概念**：项目不再提供 Workspace（工作区）概念，以及创建、选择和切换工作区的交互。所有业务 Agent 的执行和任务默认以**运行 Quartet 的系统用户的 Home 目录**作为所选 Harness Client 的工作目录，新建 Session 时同样使用该默认目录。
- **保留 Graph Workflow 功能**：当前 Graph Workflow 页面及相关功能**全部保留，保持现状，不做改动**。
- **数据存储载体**：v2.0 的数据存储继续采用 **JSONL 文件形式**，**不使用 SQLite**。聊天原文按 Session 保存，会话目录、摘要和检索索引同样使用 JSONL 持久化；**索引作为可重建的加速数据**，可根据原始记录重新生成。

## 设计原则与边界

- **群聊长期存在，Session 按需轮换**：每个 Quartet 实例提供一个共享首页群聊。切换 Agent、新建 Session、开启独立任务都不切断首页时间线；记录消息发起账号，账号之间继续共享业务数据，RBAC 只控制功能能力。
- **新首页采用独立的群聊业务链路**：负责消息路由、任务归属、Session 选择、排队和结果回流。复用现有 ACP 接入、Harness Client 安装认证、执行资源管理及文件能力，避免把整条首页对话装进一个永久运行的 Job。
- **重构不考虑兼容性**：按 v2.0 的交互和数据关系设计，不为旧普通聊天接口、会话格式及 Workspace 附属配置保留兼容链路，也不要求自动迁移或合并。新首页使用全局消息预设，旧工作区级预设不自动合并；Graph 功能和数据按下述保留边界处理。
- **Graph Workflow 保持现状**：保留页面、编排、运行控制、历史、分享、Hook 和定时触发。现有 Job、Session 及其存储继续服务 Graph；其原有执行工具选择保持 Harness Client 的含义，不自动转换为新首页的业务 Agent。旧工作区路径仅作为内部数据定位信息，不进入新首页的产品概念；必要的入口和默认目录适配放在两条业务链路的边界。
- **默认目录与数据目录分开管理**：新启动的 Harness Client 默认使用运行 Quartet 的系统用户 Home，应用配置、聊天记录、运行状态和缓存仍由 LOCAL_MEMORY 统一管理。Home 无法解析时明确报错，不回退到服务启动目录。已有 Graph 的显式目录配置与历史数据不被覆盖。
- **保留现有公共能力**：登录权限、设置、统计、文件和调度按原有能力保留。**业务 Agent 管理角色与 SystemPrompt，Harness Client 管理安装、认证、版本、能力和用量**，沿用现有执行工具管理能力。IM 保留平台登录、消息接入规则、媒体收发与主动推送能力，**对话入口改接统一首页群聊**，不再独立组织 Workspace、Job 和对话历史。JSONL 用于新增群聊数据，不借本次改造强制重写 Graph 和现有公共配置的存储格式。

## 核心对象与数据关系

| 对象 | 职责与关系 |
| --- | --- |
| **Harness Client** | 通过 ACP 接入的 Codex、Claude Code 等执行工具，继续负责安装、认证、版本、模型能力探测与实际运行 |
| **业务 Agent** | 用户可以 @ 的稳定身份，拥有名称、SystemPrompt 和可选的默认 Harness Client 偏好，实际运行后端可在对话框选择。主 Agent 默认存在，可不配置；多个业务 Agent 可以使用同一个 Harness Client |
| **群聊** | Web、iOS 和 IM 消息的共同归属，提供统一时间线、历史分页和实时订阅 |
| **任务（对话分支）** | 负责后续消息和执行结果的归属，包括默认对话、显式独立任务和主 Agent 派发的子任务；保留任务名称及父子关系 |
| **Session** | 某个任务中某个业务 Agent 在选定 Harness Client 下的连续上下文，固定关联该执行后端及其底层 ACP 会话；同一任务可以先后使用多个 Session |
| **执行记录（Run）** | 一次用户消息处理或子任务执行，记录业务 Agent、实际 Harness Client、模型及运行配置，关联任务、Session、触发来源和执行状态；与长期任务的生命周期分开 |
| **消息** | 用户消息和 Agent 回复，关联发送者、实际目标、任务、来源执行和引用关系；保留来源渠道与回传目标，拥有稳定标识及群聊内顺序 |
| **执行详情** | Agent 返回的思考内容、工具调用、结果和执行过程，关联对应回复；内部提示另有内容类型和可见性标记 |

- **当前 Session 按“任务 + Agent”确定**。同一个 Agent 的主对话、独立任务和子任务各自维护上下文，不能只按 Agent 查找全局最后一个 Session。
- **身份与执行选择分别记录**：业务 Agent、Harness Client、业务 Session 和底层 ACP 会话分别标识，不能共用一种 Agent 身份。**一个 Session 的 Harness Client 固定不可变**；切换后端时创建新的业务 Session 和底层 ACP 会话，业务 Agent 和任务归属保持不变，旧 Session 的后端绑定和历史记录保留。
- **用户消息只生成一个可见条目**。主从派发和历史引用保留原消息关联，向其他 Session 提供上下文时不重复制造用户发言。
- **时间线顺序由后端确认顺序决定**，不依赖不同设备的时钟。流式回复更新原消息，切换 Session、刷新和历史回填都不重新排序已有消息。

## 消息路由与 Session 生命周期

| 发送方式 | 路由与处理规则 |
| --- | --- |
| **普通发送，未 @ Agent** | 进入主 Agent 的默认对话任务；忙碌时在该任务的当前 Session 排队 |
| **IM 普通消息** | 经同一入口进入主 Agent 的默认对话任务，与首页共用当前 Session 和队列；来源渠道本身不触发新建独立会话 |
| **@ 指定 Agent** | 进入该 Agent 的默认对话任务；回复同一 Agent 的某个任务时沿用该任务 |
| **回复某个任务，未另行 @** | 使用该任务对应的 Agent 和上下文，不改变普通发送的默认目标 |
| **开启独立任务** | 为选定 Agent 创建新任务和新 Session，原任务继续；新任务不会自动替换默认对话任务 |
| **停止并发送** | 暂停目标任务的普通队列，确认当前执行停止后，在原 Session 优先处理新消息；原排队消息保留，等待用户继续或撤回 |

- **明确接收目标**：首版每条消息选择一个直接接收 Agent，多 Agent 协作通过编排完成。显式 @ 优先确定目标；若与被回复任务的 Agent 不同，则进入目标 Agent 的默认任务，并保留被回复消息的引用。目标不可用时展示完整错误，不悄悄改投主 Agent。
- **主 Agent 无需先行配置**：系统初始化时提供默认业务主 Agent 和角色指令；未显式选择时，Harness Client 与模型沿用默认偏好，用户可以直接进入对话，之后在输入框按需修改。Harness Client 未安装或未认证时沿用现有安装认证流程，业务 Agent 身份仍然保留。
- **服务端确认选择并固定归属**：接收发送请求时校验用户选择的业务 Agent、Harness Client 和运行配置，统一确定任务与 Session，并保存本次配置版本。已接受的消息不会因之后切换执行后端、主 Agent 配置变化或其他分支新建 Session 而改投。
- **超时只在空闲边界判断**：空闲阈值**默认 30 分钟，可在设置中调整**。执行中、停止中、等待澄清或权限确认，以及有待处理消息时，均不因超时新建 Session。从最后一次执行结束与待处理队列清空两者中较晚的时刻计算空闲时间，超过配置阈值后在下一次发送时新建；修改阈值不改变已接受消息的归属。
- **Session 轮换保留衔接**：新 Session 沿用原任务，保留上一 Session 的关联，并注入有长度限制的已确认决定和未完成事项；聊天原文继续可检索。显式独立任务只带本次输入、引用内容和必要历史概览。
- **配置变更有明确生效点**：业务 Agent 的身份与配置版本分别保存。SystemPrompt 或 Harness Client 变更在新 Session 中生效，运行中的执行、已接受的排队消息和历史记录保持原配置关联；并发占用或租约冲突通过排队处理，不重置 Session。

## 对话框中的 Harness Client 选择

- **区分两个选择维度**：@ 列表只展示业务 Agent；输入框的执行后端选择器展示 Harness Client。沿用现有输入框中的模型、模式、思考级别和用量控件，选项随 Harness Client 的实际能力更新，不把后端名称当作新的业务角色。
- **按任务保留运行偏好**：输入框恢复当前任务中该业务 Agent 上一次确认的 Harness Client 与运行配置。新任务未显式选择时，使用该业务 Agent 的默认偏好，再回落到系统默认；切换 @ 对象时恢复对应 Agent 的选择，不把前一个 Agent 的后端配置直接带过去。
- **切换后端必须使用新 Session**：同一个业务 Agent 从 Codex 切换为 Claude Code 时，即使未超过空闲阈值，也必须为新后端创建新的业务 Session 和底层 ACP 会话；之后切回 Codex，同样创建另一段新 Session，不自动恢复之前的 Codex Session。新选择首次提交消息时创建 Session，沿用该业务 Agent 的角色指令、原任务和必要衔接摘要，历史回复仍标明实际使用的 Harness Client。
- **切换不打断已接收工作**：选择新 Harness Client 后，后续提交的消息绑定新的执行选择；同一任务仍按接收顺序串行处理，原执行及其已接受的队列先完成，新 Session 再开始。需要立即并行时，通过独立任务使用另一个 Harness Client。
- **多端和后台沿用明确选择**：IM 没有执行后端选择器时，沿用主对话当前确认的 Harness Client；有任务引用时沿用对应任务的选择。从 Agent 的子任务可使用自己的默认 Harness Client，派发时也可明确指定，不能仅因主 Agent 使用 Codex 就强制所有从 Agent 使用 Codex。
- **配置可用性显式反馈**：所选 Harness Client 未就绪、模型不可用或运行参数不受支持时，展示完整原因并保留待发送内容，不悄悄换成其他执行后端或业务 Agent。正文显示业务 Agent 身份，回复详情可查看实际 Harness Client 和模型；版本、套餐及额度仍按既有顺序展示。

## 任务执行与主从编排

- **同一任务和 Session 串行，不同任务可并行**：每个 Session 同时只有一个执行，同一任务在 Session 或 Harness Client 切换期间也保持顺序。不同任务受全局、Harness Client 及账号可用并发约束；资源不足时保持可见的等待状态，不额外创建 Session 绕开限制。
- **接收与执行分开确认**：客户端重试使用同一发送标识，重复提交返回已有处理状态。同一标识对应不同内容时明确报错。用户消息可靠保存后才能显示“已接收”，真正开始处理后才显示“处理中”。
- **队列可恢复、可撤回**：等待消息按接收顺序处理，开始执行后不再允许当作排队消息撤回。**排队期间只保存接收与队列记录，开始处理时才把消息加入 Session 的实际输入**，避免未处理消息提前进入当前执行的上下文。执行失败、等待用户输入或停止确认未完成时，暂停该分支后续派发并显示原因；权限确认、澄清回答和停止控制直接关联原执行，不进入普通消息队列。
- **停止确认是下一轮的前提**：停止请求发出后保持“停止中”，收到原执行结束确认才启动“停止并发送”的新消息。停止超时或失败时保留完整错误及待发送内容，不并发启动下一轮。取消完成的判定沿用 [ACP 轮次与取消语义](https://agentclientprotocol.com/protocol/v1/prompt-turn#cancellation)。
- **主 Agent 通过 Quartet 派发子任务**：统一任务能力经 quartet-cli 和共享 Skill 提供，负责指定从 Agent、任务说明、必要上下文及期望结果。每个独立子任务有自己的任务分支、Session 和状态；任务接受后，主 Agent 可以结束当前轮次继续对话。
- **结果回到原任务**：从 Agent 的输出关联原派发任务，可在群聊中按对应身份展示。需要主 Agent 汇总时，将结果作为内部待处理项送回父任务，与该任务的其他输入串行处理，并按来源执行去重。父任务已切换 Session 时交给该任务当前可用 Session，携带原派发关联，不抢占其他任务；目标不可用时保留结果和待回流状态，并展示完整原因。
- **后台工作有独立控制入口**：主 Agent 一轮结束不代表其子任务结束；每个后台任务展示状态、结果和停止入口。停止某个执行不隐式影响其他独立任务，失败结果也必须回流，不能只回报成功。
- **重启不盲目重放执行**：已接收但未开始的消息恢复为待处理；运行中失去进程的执行标记为中断，保留已产生内容并显示原因，由用户选择重试。发送去重和结果去重不等于外部工具副作用可以自动重放。

## IM 接入与回复回传

- **渠道接入共用首页业务链路**：通过现有 IM 接入规则的消息，经统一接收、持久化、路由和排队后进入首页。保留已支持的文本、图片和文件能力，媒体沿用现有文件存储；IM 消息及对应回复纳入同一套历史检索。
- **同一主对话跨渠道连续**：IM 普通消息与 Web、iOS 的普通消息共用主 Agent 的默认任务和当前 Session，执行、排队和 30 分钟空闲轮换规则一致。平台能提供有效消息引用时，可通过原消息关联继续对应任务；没有可识别目标或引用时默认交给主 Agent。
- **回传目标固定到触发消息和执行**：保留平台、接入账号、原会话、发送者和原消息关联；每次执行及其派发的子任务沿用该次输入的回传目标。多个 IM 会话或 Web 输入交错到来时，不能根据同一 Session 最近一条消息的来源决定回复去向。
- **正文按来源回传，首页统一展示**：IM 发起的对话回复及后续后台任务结果回到原平台、原会话，同时保留在首页。Web、iOS 发起的其他回复不自动广播到 IM，思考、工具过程和内部提示不作为普通 IM 回复外发。
- **接收去重与投递恢复分别管理**：按平台、接入账号、原会话和原消息识别重复投递，重复接收不重复触发 Agent。外发保存独立投递状态，失败时在首页展示完整错误；重试只处理回复投递，不重新执行 Agent。原平台无法确认送达时，明确保留未知状态。
- **主动推送保留原有能力**：主动发送记录及其投递状态在首页可追溯；系统自身发送的消息回显不作为新用户输入再次触发主 Agent。

## JSONL 存储与一致性

新增群聊数据由后端统一管理，Agent 通过服务能力读写，不自行修改持久化文件。区分以下逻辑记录：

- **提交记录**：保存已接受的消息、路由决定、执行状态变化及结果回流，是判断一次操作是否被系统接受和跨文件恢复的依据。
- **Session 原文**：按 Session 保存实际输入、Agent 回复和执行详情，保留消息标识、内容类型和来源关联；实际输入**完整保留 `<system-reminder>` 标签、内部内容和原始拼接顺序**。普通模式隐藏内容仅生成展示视图，不删改原文；摘要生成也不截断或替换原文。
- **群聊时间线**：保存可见消息的顺序、版本和来源引用；排队消息引用接收记录，已投递消息及 Agent 回复关联 Session 原文，不再复制一份独立演进的聊天正文。
- **Agent、Harness Client、任务和 Session 目录**：分别保存业务角色配置、Harness Client 引用、任务运行偏好、父子任务关系、当前 Session、排队与停止状态；历史执行保留实际后端与运行配置，状态必须能与提交记录核对恢复。
- **IM 来源与投递记录**：保存外部消息与群聊消息、执行、原会话及回传目标的关联，记录接收去重和回复投递状态；新增记录同样使用 JSONL，可在重启后继续核对未完成投递。
- **会话卡片与检索索引**：保存摘要、覆盖进度、检索片段和定位信息，作为可重建的派生数据。附件继续使用现有文件存储，以稳定引用关联消息。

一致性要求如下：

- **单一提交入口**：同一日志由后端串行追加，每条记录完整保存后再确认接收。跨 Session 可以并行执行，但不能多个进程无协调地并发修改同一份日志。记录格式遵循 [JSON Lines](https://jsonlines.org/) 的逐行完整记录约定。
- **跨文件中断可补齐**：先可靠保存完整提交记录，再更新 Session 原文和各类目录、时间线。进程在更新中途退出时，根据提交记录补齐；已接受的消息不能因目录尚未更新而丢失，也不能被重复派发。
- **一条逻辑消息一个稳定标识**：提交记录、原文及索引中的关联保持一致。修改、撤回、状态更新和删除采用后续版本或删除标记；历史引用不以文件行号、偏移或整理后的存储位置作为身份。
- **流式内容分批保存**：合并正文和详情增量，周期保存；回复完成、失败或停止时立即保存最终内容与状态，再发布对应完成通知。异常退出时，进行中的回复恢复到最近保存的片段并标记中断，已确认消息和已完成回复保持完整。
- **分段与整理保持可追溯**：日志按大小或时间分段，状态快照仍使用 JSONL。整理完成并校验后再切换，旧引用、去重记录和删除状态不能丢失；派生目录及索引可以从原始记录重建。
- **损坏与写入错误完整可见**：不完整尾记录与中段损坏分别识别，保留问题记录及恢复说明；不能静默跳过后宣称历史完整。提交记录落盘失败时不确认成功、不继续派发依赖该提交的执行；提交已成功而后续原文或目录更新失败时，保留接收回执、展示错误并补齐更新，客户端重试仍对应同一条消息。
- **备份覆盖完整数据关系**：配置、提交记录、Session 原文和附件按一致边界备份；恢复后重新核对目录及索引，不把缓存当作唯一历史来源。

## 上下文组装与历史检索

- **角色指令与内部补充有来源区分**：SystemPrompt、历史概览、任务派发和结果回流均作为内部上下文，经 `<system-reminder>` 提供给 Agent。分别记录配置版本、来源和覆盖范围，避免每轮重复追加相同指令；这种包装不改变底层 Agent 原生系统指令的优先级。
- **完整原文与显示模式分离**：内部提示保留独立的内容类型和来源，与用户正文一起可还原实际投递的完整消息。普通模式隐藏 `<system-reminder>` 标签及内部内容；调试模式按原始位置完整展示。实时流、历史分页和刷新重建遵循所选模式，ACP 回显仍关联原消息，不因调试展示重复生成用户发言。
- **显示模式不改变执行与查询语义**：切换普通或调试模式不改变实际发送给 Harness Client 的内容，不触发新的 Session 或重新执行。Agent 的默认历史检索和 IM 回复范围继续沿用各自规则，不因首页启用调试模式而额外加入内部提示。
- **共享有限概览，保留完整查询入口**：新 Session 获得近期会话、未完成任务及工具用法；同一任务轮换时补充必要衔接摘要。每次注入有长度预算，更早历史仍可通过分页和搜索访问。
- **摘要独立维护**：**复用标题生成所选 Harness Client、模型及其默认选择规则，不新增独立摘要执行后端配置项**；通过独立的 ACP Session 执行后台摘要，不占用用户当前 Session，也不要求创建额外的摘要业务 Agent。初始参数为摘要不超过 500 字、每轮结束后合并增量更新、摘要后台并发为 1，优先保障用户对话。保留摘要所覆盖的原文版本，较旧任务不能覆盖较新摘要；维护任务自身不作为用户会话再次收录，避免递归摘要。摘要生成失败不阻断原文查询，并展示完整失败原因。
- **检索基于全量可查询原文**：默认覆盖用户消息与回复正文，摘要用于排序和导航，不能因摘要未命中而排除正文。支持中文短词、短语、时间和 Agent 筛选；长消息分段定位，返回数量、单个片段长度及总结果长度有上限，并允许继续读取。
- **命中后回看原文**：查询结果保留 Session、消息、时间、作者和上下文定位，重要结论读取原文核实，区分用户已确认决定与 Agent 建议。工具结果按需查询，内部提示不混入普通命中。
- **索引延迟不等于没有历史**：后端记录各来源的索引覆盖进度，查询时补搜尚未覆盖的原文；超时或部分来源失败时明确报告不完整范围。删除后使对应摘要和索引失效。首版使用关键词与短语检索，语义检索作为后续增强。
- **历史检索按 v2.0 会话模型建设**：旧普通对话和 Workspace 数据不要求兼容读取或自动迁移；本次首页检索不增加旧格式适配。Graph 历史继续通过现有页面和读取能力访问，原有数据写入、展示和生命周期保持不变。

## 实时同步与客户端

- **首页只保留一条群聊事件流**：统一承载不同 Agent 的正文更新、任务状态、队列变化和结果回流，不按 Session 或执行分别开连接；某个执行结束不关闭整条群聊流。Graph 页面继续遵循原有的一页一条流规则。
- **首屏快照与事件续传对齐**：客户端先获取最新消息页、任务队列状态及对应续传位置，**快照内容与续点来自同一已提交状态边界**，再接收后续事件；断线后按游标续传，游标失效则重新获取快照。消息版本用于去重和防止旧内容覆盖新内容。续传位置参考 [SSE 标准](https://html.spec.whatwg.org/dev/server-sent-events.html#the-last-event-id-header)，群聊顺序和实时事件续点分别管理。
- **正文优先，详情按需读取**：每条 Agent 回复展示正文和对应任务标识；思考及工具详情默认折叠，展开时分页读取大内容，继续执行时通过原群聊流接收变更提示，不另开长连接。尚无正文时显示处理状态，失败时单独完整展示错误，不能藏在折叠区中。
- **设置统一控制首页显示模式**：Web 和 iOS 在设置中选择普通模式或调试模式，保存后刷新及重新进入仍保留。切换时同步更新已加载消息、实时消息和后续历史分页；调试模式可查看完整的原始消息，包括 SystemPrompt、历史概览、任务派发和结果回流所包含的 `<system-reminder>` 片段，长内容按需完整加载，不丢弃或省略原文。
- **Web 与 iOS 使用同一套归属及状态规则**：发送目标、回复任务、排队、撤回、停止和独立任务均由后端裁决，客户端不能各自猜测当前 Session。刷新和多端同时操作后，已确认消息、待处理队列及执行状态一致。
- **iOS 语音以整次录音为一次发送**：基于系统语音识别能力，录音开始时确定目标 Agent 和任务；结束录音并收齐最终转写后，整体发送一次。中间候选和已定稿片段只累积展示，不分别发送；取消录音后到达的结果也不发送。最终转写的处理依据 [Apple 语音识别说明](https://developer.apple.com/documentation/speech/recognizing-speech-in-live-audio)。
- **语音异常可恢复**：按系统要求取得录音与识别授权；空结果、权限拒绝和识别失败不发送消息，并展示完整原因。发送失败保留转写文字，重试沿用原发送标识；默认只归档最终文字，不把录音作为群聊附件保存。
- **后台与查看状态沿用现有约束**：iOS 只在 scene active 时订阅，恢复前台后补齐状态；Web 同步页面可见性与重连后的查看状态。订阅群聊不等于正在查看所有后台任务，结束 Hook 按实际任务查看状态判断，用量按执行归集并去重。

## 验收标准

- [ ] Web、iOS 打开首页即可进入同一群聊，主 Agent 默认存在，无需用户先行配置；普通发送进入主 Agent，@ 和回复任务的实际目标与界面显示一致。
- [ ] @ 选择业务 Agent，输入框可独立选择 Codex、Claude Code 等 Harness Client 及其支持的运行参数；同一业务 Agent 在未超过空闲阈值时依次使用 Codex、Claude Code、再切回 Codex，对应三个不同的业务 Session，底层 ACP 会话上下文不复用；业务身份、SystemPrompt 和任务归属不变，旧记录保留可查。
- [ ] 切换 Harness Client 不改投已接受的排队消息，不打断原执行或造成同一任务并发；两个独立任务可以为同一个业务 Agent 分别选择不同 Harness Client，历史可查看实际执行后端。
- [ ] IM 消息和对应回复可在首页看到来源，与 Web、iOS 共用主对话 Session 和排队规则；不再为每个外部会话创建独立 Workspace 或 Job。
- [ ] 来自两个 IM 会话的输入及 Web 输入交错处理时，各次回复和后台结果仍回到正确原会话，不串发或自动广播；重复平台投递不重复执行 Agent，回传失败重试不重新执行 Agent。
- [ ] 同一 Agent 的两个独立任务使用不同 Session，可并行产生回复；普通发送始终进入默认对话，回复指定任务继续对应分支。
- [ ] 当前 Session 忙碌时，新消息按顺序等待，开始处理前可撤回；停止尚未确认时，下一轮不会启动，失败原因完整显示。
- [ ] 默认空闲超过 30 分钟后，下一次发送新建 Session，阈值可配置，原任务和首页历史连续；执行、排队及等待用户输入不触发轮换。
- [ ] 主 Agent 派发后可继续对话，子任务成功与失败均回到原任务；重连、重复提交和重复结果通知不重复执行或重复生成同一消息。
- [ ] JSONL 中可恢复已接受消息、任务状态和 Session 原文；模拟跨文件写入中断后，能补齐记录。运行中异常退出显示中断，不自动重放未知副作用。
- [ ] 摘要复用标题生成所选 Harness Client，以独立 Session 后台执行；删除派生索引后可重建。摘要尚未更新时，最新已保存原文仍可查询；中文短词、跨 Agent 和较早的 v2.0 会话检索可返回原文定位，部分失败明确显示不完整范围。
- [ ] 普通模式下，`<system-reminder>` 标签及内部内容在实时、刷新和历史分页中均隐藏；调试模式下，能按原始位置查看包含标签及内部内容的完整消息，已保存历史也可切换查看。
- [ ] 显示模式可在设置中切换并持久化，切换不改变实际执行输入、不新建 Session、不重复执行或重复产生消息；Agent 默认历史搜索和 IM 外发规则不受影响。思考及工具内容属于正确回复，默认折叠，展开不增加长连接。
- [ ] iOS 一次录音只发送一条最终文本，取消、空结果或识别失败不发送；网络失败后重试不重复生成消息。
- [ ] Graph 页面、已有运行记录、编辑校验、运行恢复、停止、分享、Hook 及定时执行保持原有行为，不要求用户创建或切换 Workspace。
- [ ] 新首页无需旧普通对话或工作区数据即可初始化，使用全局消息预设，不依赖旧接口、旧格式兼容或工作区配置自动合并。
- [ ] 端到端验证覆盖 Web 浏览器与 iOS；身份权限、文件、IM、统计及查看状态无功能回退，所有错误信息可完整查看。

## 已确认事项

- **首页显示模式**：设置提供普通模式和调试模式，默认普通模式；普通模式隐藏 `<system-reminder>` 标签及内部内容，调试模式展示完整消息，仅影响首页展示。
- **空闲轮换**：默认 30 分钟，允许配置；执行结束且队列清空后开始计算空闲时间，等待澄清或权限确认时不轮换。
- **主 Agent**：默认存在并提供默认配置，用户可以不配置，之后按需调整。
- **业务身份与执行后端**：Agent 表示业务角色；Codex、Claude Code 等称为 Harness Client，在对话框独立选择。**同一 Agent 每次切换 Harness Client，都必须为后续消息新建 Session**，不受空闲时长限制，切回原后端也不自动复用旧 Session；业务身份和任务保持不变。
- **摘要执行后端**：复用标题生成所选 Harness Client，使用独立 Session 执行后台摘要。
- **IM 入口**：接入当前首页群聊，普通消息默认进入主 Agent 的主对话，回复按触发消息来源回传。
- **兼容性**：重构不考虑兼容性，不要求兼容读取、自动迁移或合并旧普通对话及 Workspace 附属配置；Graph 既有功能和数据继续保留。
