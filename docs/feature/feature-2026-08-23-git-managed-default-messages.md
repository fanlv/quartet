# Git 管理的全局 / 项目默认消息

> 状态：待实施
> 范围：Web 设置页、首页输入框、Job 对话输入框、Memory 持久化

## 1. 背景

当前首页和 Job 对话页都提供“本地历史”列表。发送内容按 workspace 保存在浏览器本地，最多保留最近 50 条；用户点击发送后即写入，不依赖消息最终是否发送成功。

这套能力适合临时回看，但存在以下限制：

- 换浏览器或设备后无法复用。
- 不能区分“临时发送记录”和“长期保留的常用内容”。
- 不能为全部项目或某个项目预先维护固定消息。
- 浏览器数据不进入 Memory 仓库，无法通过 Git 审阅、同步和恢复。

本功能新增“默认消息”。默认消息是用户主动选择后填入输入框的预置文本，不是自动发送规则，也不是对话上下文。

文档中的“项目”对应 Quartet 的 workspace。项目级配置始终绑定稳定的 workspace ID，不绑定项目名称或工作目录。重命名项目或修改工作目录不会导致配置失效。

## 2. 目标

- 在设置页维护多条默认消息。
- 每条配置归属于“全部项目”或一个具体项目。
- 当前项目的输入框可以同时使用项目默认消息和全部项目默认消息。
- 默认消息保存到 Memory 的 Git 可跟踪配置目录。
- 保留现有浏览器本地历史及其交互，不把高频历史记录写入 Git。
- 配置错误、权限错误和写入错误完整展示给用户，不静默忽略。

## 3. 核心规则

### 3.1 默认消息不会自动发送

选择默认消息后，只把原始文本填入输入框，由用户检查、编辑并再次确认发送。系统不得在进入项目、创建 Job、切换项目或点击列表项时自动发出消息。

默认消息可以包含多行文本、斜杠命令和文件引用文本，填入时保持原始内容，不做变量替换或 Prompt 渲染。

### 3.2 作用域与合并规则

| 配置范围 | 生效位置 | 列表位置 |
| --- | --- | --- |
| 全部项目 | 每个 workspace 的首页和 Job 输入框 | “全部项目”分组 |
| 指定项目 | 仅 workspace ID 完全匹配的首页和 Job 输入框 | “当前项目”分组 |

项目配置采用补充关系，不覆盖全局配置：

1. 当前项目消息排在最前。
2. 全部项目消息排在其后。
3. 浏览器本地历史排在最后。
4. 各分组内部使用设置页中保存的顺序。
5. 不跨分组自动去重。同一文本可能既是默认消息，也出现在最近发送历史中，两者分别保留并显示来源。
6. 项目没有专属配置时，只展示全部项目消息和本地历史。

默认 workspace `ws-1` 也按普通项目处理：它可以拥有自己的项目级默认消息，同时继承全部项目消息。

### 3.3 与本地历史的关系

两类内容保持独立：

| 内容 | 保存位置 | 生命周期 | 用途 |
| --- | --- | --- | --- |
| 默认消息 | Memory Git 配置目录 | 长期、可同步、可恢复 | 主动维护的常用文本 |
| 本地历史 | 浏览器 localStorage | 单浏览器、每项目最近 50 条 | 回看最近实际发送内容 |

- 本功能不迁移已有本地历史。历史里可能包含失败发送、图片、临时信息或敏感内容，不能未经确认写入 Git。
- 由默认消息填入并实际发送后，仍按现有规则进入本地历史。
- 键盘 `ArrowUp` / `ArrowDown` 继续只遍历本地历史，不遍历默认消息，避免改变“上一条已发送内容”的语义。
- 默认消息首期只保存文本，不保存图片、附件或本地文件副本。

## 4. 设置页设计

设置中新增独立的“默认消息”页签，避免把全局配置塞入某个项目的编辑弹窗。

页面包含：

1. **作用域选择**：可选择“全部项目”或一个现有项目。
2. **消息列表**：展示当前作用域下的消息名称、内容预览和顺序。
3. **新增 / 编辑**：名称可选，正文必填；未填写名称时使用正文第一行作为列表标题。
4. **排序**：支持调整同一作用域内的展示顺序。
5. **删除**：删除前确认，保存后形成普通 Git 文件变更。
6. **保存状态**：明确展示未保存、保存中、已保存、版本冲突或失败。

交互约束：

- 切换作用域或关闭设置页时，如果存在未保存修改，必须提示用户确认。
- 空列表是合法配置，表示该作用域没有默认消息。
- 项目名称相同也不影响选择，列表需要同时展示名称和工作目录以帮助区分。
- 页面不得因为某个错误只显示“保存失败”；必须展示服务端返回的完整错误。
- 保存成功后，当前打开的首页和 Job 输入框应立即刷新默认消息，不要求刷新整个页面。

## 5. 输入框中的展示与使用

首页输入框和 Job 对话输入框共用同一套行为。现有“本地历史”按钮调整为“默认消息与历史”入口，弹层按以下分组展示：

1. 当前项目
2. 全部项目
3. 最近发送

没有内容的分组不展示；三个分组都为空时展示统一空状态。每一项显示名称或正文预览，并以标签明确来源，长文本可查看完整内容。

用户点击默认消息时：

- 用默认消息正文替换输入框当前文本。
- 保留输入框中已经选择或上传的图片。
- 关闭选择列表并把焦点放回输入框。
- 不创建 Job、不触发发送、不写本地历史。

用户点击最近发送历史时，继续沿用当前的文本和图片恢复行为。默认消息读取失败时，本地历史仍然可用，输入框和发送能力不得被禁用；列表内同时展示完整错误，便于用户修复 Memory 配置。

## 6. Memory 存储与 Git 语义

### 6.1 目录规划

默认消息保存到 Memory 中面向人工维护、可被 Git 跟踪的配置区域：

```text
$LOCAL_MEMORY/quartet/config/default-messages/
├── global.json
└── workspaces/
    ├── ws-1.json
    └── <workspace-id>.json
```

- `global.json` 保存“全部项目”消息。
- 每个项目使用独立文件，文件名采用稳定的 workspace ID。
- 不写入 `$LOCAL_MEMORY/quartet/data/`；当前 Memory 仓库会忽略该目录，无法满足 Git 管理要求。
- 不写入通用 `settings.json`，避免默认消息与包含其他设置的整文件保存互相覆盖，也便于 Git 单独审阅某个项目的变更。

每个作用域文件包含格式版本和有序消息列表。每条消息包含稳定 ID、可选名称和正文。顺序以文件中的列表顺序为准，不依赖更新时间排序。

### 6.2 Git 行为

- 设置页保存成功后，文件立即落盘并在 Memory 仓库中表现为普通未提交变更。
- Quartet 不自动执行 `git add`、`git commit`、`git pull` 或 `git push`。提交、同步和冲突处理继续由现有 Memory 管理流程负责。
- Git 切换、拉取或回滚配置后，重新打开列表或刷新页面即可读取新内容，不要求重启后端。
- Git 中出现无法解析、版本不支持、ID 重复或字段不合法的配置时，不做静默修复；读取接口返回完整文件位置和错误原因。
- 文件写入采用完整替换语义。保存失败时保留原有效配置，不产生只写入一部分的结果。
- 默认消息属于共享配置，会进入 Git 历史，并对有权使用对应项目的账号可见。设置页需要明确提示不要保存密码、令牌或其他秘密。

### 6.3 项目生命周期

- 项目重命名和工作目录变更不影响配置。
- 删除项目时，同时删除对应的默认消息配置文件，并在确认信息中明确提示；该删除会表现为可通过 Git 恢复的文件删除。
- 如果外部 Git 操作恢复了一个已不存在项目的配置文件，该配置不参与任何输入框的有效列表；设置页将其标记为“项目不存在”，允许具备全局配置管理权限的用户清理。

## 7. 数据校验与并发

- 正文去除首尾空白后不能为空，但保存和填入时保留用户输入的内部换行和格式。
- 同一作用域内消息 ID 必须唯一；名称可以重复。
- 单个作用域最多 100 条消息，单条正文最多 32 KiB，可选名称最多 80 个字符。超限时拒绝保存并显示具体条目和限制。
- 保存请求必须携带读取时获得的不透明修订标识。文件内容发生任何变化时，包括设置页保存和外部 Git 修改，修订标识都必须变化。
- 修订标识不一致时返回冲突及服务端当前修订，不能用旧页面覆盖新内容。
- 全局和各项目使用独立修订；编辑某个项目不会阻塞或覆盖其他项目。
- 外部 Git 修改与页面保存发生冲突时，不自动合并。用户刷新最新配置后再处理差异。

## 8. 服务能力与权限边界

需要提供以下业务能力，具体接口命名可在实施时沿用现有 API 风格：

- 读取当前项目的有效默认消息，同时返回“当前项目”和“全部项目”的来源信息。
- 单独读取、保存全部项目配置。
- 单独读取、保存指定项目配置。
- 列出已不存在项目的孤儿配置，供设置页清理。

权限规则：

- 拥有 `workspace.read` 的用户可以读取当前项目的有效默认消息。
- 在设置页查看全部项目配置需要 `config.read`，修改需要 `config.write`。
- 在设置页查看现有项目配置需要 `workspace.read`，修改需要 `workspace.write`。当前共享实例不做账号级项目隔离，拥有该权限的用户可以修改任意项目。
- 清理不存在项目的孤儿配置需要 `config.write`。
- 后端必须执行最终权限校验；前端隐藏按钮不能替代授权。

默认消息使用独立的读写能力，不通过“读取整份设置、修改一个字段、再保存整份设置”的方式更新，避免并发页面相互覆盖。

## 9. 用户故事与验收标准

### US-001：配置全部项目默认消息

**用户故事：** 作为配置管理员，我希望维护所有项目都能使用的默认消息，以便统一复用常用指令。

**验收标准：**

- [ ] 设置页可以选择“全部项目”，新增、编辑、删除和排序多条消息。
- [ ] 保存后内容写入 `$LOCAL_MEMORY/quartet/config/default-messages/global.json`。
- [ ] 任意项目的首页和 Job 输入框都能看到这些消息。
- [ ] 点击后只填入输入框，不自动发送。
- [ ] 使用浏览器验证设置保存、列表刷新和输入框填入行为。

### US-002：配置指定项目默认消息

**用户故事：** 作为项目维护者，我希望为某个项目配置专属消息，以便快速执行该项目常见任务。

**验收标准：**

- [ ] 设置页可以选择一个现有项目并维护其独立消息列表。
- [ ] 项目配置按 workspace ID 保存，不因改名或改变工作目录失效。
- [ ] 专属消息只出现在匹配项目中，不出现在其他项目中。
- [ ] 当前项目消息排在全部项目消息之前。
- [ ] 使用浏览器切换至少两个项目验证作用域隔离。

### US-003：与本地历史共同使用

**用户故事：** 作为聊天用户，我希望在同一入口使用默认消息和最近发送历史，同时能辨认其来源。

**验收标准：**

- [ ] 列表按“当前项目 / 全部项目 / 最近发送”分组，并隐藏空分组。
- [ ] 选择默认消息保留已有图片，只替换输入文本。
- [ ] 选择本地历史继续恢复历史文本和图片。
- [ ] 键盘上下键仍只遍历本地历史。
- [ ] 默认消息发送后正常进入最近发送历史，但不会修改默认消息配置。
- [ ] 桌面和移动布局均通过浏览器验证。

### US-004：通过 Git 审阅和恢复

**用户故事：** 作为实例维护者，我希望默认消息表现为 Memory 仓库中的普通配置变更，以便提交、同步和回滚。

**验收标准：**

- [ ] 新增、编辑、排序和删除均产生范围明确的 Git diff。
- [ ] 默认消息文件不受 Memory `.gitignore` 排除。
- [ ] Quartet 不自动提交或推送这些变更。
- [ ] Git 回滚后刷新页面即可看到恢复内容，无需重启后端。
- [ ] 非法配置返回完整错误，不影响本地历史和输入框发送。

### US-005：避免并发覆盖

**用户故事：** 作为共享实例用户，我希望过期的设置页面不能覆盖别人刚保存的默认消息。

**验收标准：**

- [ ] 两个页面编辑同一作用域时，后保存的过期版本收到明确冲突。
- [ ] 同时编辑不同项目时可以分别保存，配置不会相互覆盖。
- [ ] 冲突响应包含完整原因和当前修订信息。

## 10. 功能要求

- **FR-1**：系统必须支持“全部项目”和“指定项目”两种默认消息作用域。
- **FR-2**：系统必须按“项目消息、全部项目消息、本地历史”的固定顺序展示。
- **FR-3**：选择默认消息必须只填充输入框，不得自动发送。
- **FR-4**：默认消息必须保存到 Memory 的 Git 可跟踪配置目录。
- **FR-5**：浏览器本地历史必须继续保留，且不得自动迁移到 Git。
- **FR-6**：首页与 Job 对话页必须使用相同的读取、分组和选择规则。
- **FR-7**：配置保存必须具备版本冲突保护，并按作用域独立更新。
- **FR-8**：读取或保存失败必须向用户展示完整错误，同时不得禁用正常聊天。
- **FR-9**：项目配置必须绑定 workspace ID，不得绑定名称或 workdir。
- **FR-10**：所有新增私有能力必须按读取和修改动作执行后端权限校验。

## 11. 非目标

- 不自动发送默认消息。
- 不把默认消息自动注入 Agent system prompt 或每轮上下文。
- 不同步、迁移或 Git 管理现有浏览器本地历史。
- 不保存图片、附件、语音或其他多媒体默认消息。
- 不提供变量、条件、模板渲染、定时发送或工作流触发能力。
- 不记录默认消息的使用次数、最近使用时间或使用人。
- 不自动提交、拉取、合并或推送 Memory Git 仓库。
- 不扩展到 iOS 或 IM 客户端；本期只覆盖 Web 首页和 Job 对话输入框。

## 12. 实施顺序

1. 建立 Git 可跟踪的默认消息存储、校验、版本冲突和权限能力。
2. 增加设置页作用域选择与消息管理。
3. 统一首页和 Job 输入框的默认消息读取与列表交互。
4. 验证 Git diff、外部回滚、项目切换、权限错误和非法文件场景。
5. 完成前端构建，并在桌面和移动浏览器中验收；不由 agent 执行 `make web` 重启后端。
