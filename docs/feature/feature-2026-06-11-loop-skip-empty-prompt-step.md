# Loop 空提示词步骤跳过：完整提示词为空时不执行该步骤

## 1. 背景与目标

**现状**：Loop 流程中，Shell 步骤可以通过控制文件 / 输出标记设置变量，后续 prompt 步骤的提示词里用 `{{变量名}}` 引用。典型场景：Shell 脚本检查播客 / 博客是否有更新，把待处理内容写入变量，下一个 prompt 步骤交给模型处理。

问题在于：当上游没有新内容时，脚本只能把变量设成空字符串，但后续 prompt 步骤**仍然会执行**——照样创建新会话（可能拉起一个 agent 子进程）、向模型发送一条空消息、白跑一轮。既浪费资源，聊天流和进度里也会留下一轮无意义的记录。

**判定口径说明（避免误读）**：本方案的判定对象是**变量替换后的完整提示词**，不是「某个变量是否为空」。提示词里若有固定正文（如「请处理以下内容：」）再拼一个空变量或未定义变量，替换后整体仍非空，**不会跳过**——会照常把这条提示词发给模型。需要「无内容就不跑」的场景，应让提示词模板整体只由变量构成（或让脚本把完整提示词写进变量）；模板恰好只由**一个**变量构成时，该变量未定义（占位符原样残留）与值为空一样视为「本轮无事可做」。详见 §5 边界条件。

**目标**：prompt 步骤的提示词经过变量替换后若为**空字符串**（仅含空白也算空）**或恰好只剩一个 `{{变量}}` 占位符**（整条提示词只由一个变量构成且替换后未被解析，见三条约束之约束 1），则该步骤本轮**跳过执行**——不创建会话、不调用模型、聊天流中不出现这一轮，同时：

1. **进度分母实时下调**：跳过的步骤从总步数中扣除并立即推送给已连接的页面，进度条不会因为「少跑了一步」而卡在 100% 以下，也不会把跳过记成「完成 +1」虚增完成数。
2. **会话计划同步收缩**：Loop 进度区的「Session X / Y · Step M / N」基于剔除跳过步骤后的真实计划计算。一个只包含被跳过步骤的会话（如独占新会话的步骤被跳过）整体从计划中消失，不显示无用的 Session。
3. **跳过可观测**：跳过不在聊天流中制造噪音，但必须留下可追溯的痕迹——后端日志记录每次跳过（路径 + 原因），进度区展示累计跳过步数。否则脚本 bug 导致变量恒为空时，用户只会看到任务瞬间完成、分母缩水，无从排查。

三条约束：

1. **跳过信号无歧义**：判定只看运行期变量替换后的**完整提示词**，两条规则——
   - trim 后为空字符串，跳过；
   - trim 后**恰好是一个未解析的 `{{变量}}` 占位符**（整条提示词只由这一个变量构成、且该变量未定义导致占位符原样保留），跳过。典型场景首轮即如此：提示词模板就是 `{{items}}`，Shell 步骤还没运行、变量尚未定义，占位符原样发给模型同样是白跑一轮。

   除此之外不追踪「是否有变量参与替换」。**含固定正文**的提示词引用了未定义变量（如「请处理：{{items}}」），占位符原样保留、整体非空也不是单个占位符，照常执行——固定正文说明用户有意发送内容，不会把这类配置错误悄悄吞掉；只有「整条提示词 = 单个变量」时，未定义与空值才共享「本轮无事可做」的语义。
2. **记账始终自洽**：跳过必须同步修正进度分母并持久化，不允许「静默短路但分母不变」（那会让进度永远到不了 100%）。组提前退出（STOP_LOOP / 评估器停止）的分母回填数学、Stop → Continue 恢复、进程重启恢复、配置编辑后的进度核对，在存在跳过步骤时都要保持一致。
3. **范围最小化**：只对 prompt 类型步骤生效。评估器步骤不参与跳过（跳过会让循环失去停止判定）；Shell 步骤不参与（它本身就是产生变量的一方）。交互式发送不走此逻辑。

## 2. 设计选型

### 2.1 跳过语义：空提示词 = 本轮无事可做

- 判定时机在**该步骤即将执行之前、创建会话之前**：先注入每轮内置变量，再做变量替换，替换结果满足任一条即跳过——
  1. 去除空白后**为空**；
  2. 去除空白后**恰好是一个未解析的 `{{变量}}` 占位符**（模板整条只由一个变量构成、变量未定义）。

  判定提前到会话创建之前是关键——典型场景里这种步骤配置为「每轮新会话」，跳过的步骤绝不应该先拉起一个 agent 子进程再发现无事可做。
- **单占位符规则的边界**：占位符须是合法变量引用形态（`{{` + 变量名 + `}}`，与替换器识别的形态一致）；「`{{a}}{{b}}`」「正文 + `{{a}}`」「`{{a}} {{b}}`」都不是单个占位符，照常执行。变量**已定义**时永远走值本身的判定（值为空 → 规则 1 跳过；值非空 → 执行），单占位符规则只覆盖「未定义、原样保留」这一种残留形态。
- 跳过的步骤**完全不产生轮次**：不发轮次开始 / 结束事件、不记迭代结果、聊天流中无任何痕迹。这与「失败」「停止」都不同——它是计划内的「本轮无事可做」，不应制造噪音。后端以一条 INFO 日志（含步骤路径与命中的规则）记录每次跳过，作为唯一的执行侧痕迹。
- 不需要 `nop` 之类的哨兵值约定：脚本把变量显式设为空字符串即是明确的跳过信号。
- 步骤配置校验维持不变：校验的是模板原文（含 `{{变量}}` 占位符的非空文本），与运行期替换后为空不冲突。注意「模板只写一个 `{{变量}}`」是合法且典型的配置，**不会**被恒久跳过——一旦 Shell 把变量设为非空值，步骤照常执行。

### 2.2 配套调整：`quartet_set` 空值不再改写为 `STOP_LOOP`

现状中 Shell 内置助手 `quartet_set` 在传入空值时会把变量值改写为字面文本 `STOP_LOOP`，这带来两个问题：

1. **同一字面值跨层语义分裂**：`STOP_LOOP` 在控制文件整行出现意为「停止整组循环」；若它再被用作「提示词为空」的跳过信号，同一个词在不同层含义相反（一个停循环、一个跳单步继续循环），是长期的认知负担。
2. **污染混合模板**：「请处理以下内容：{{items}}」拼上被改写的空变量，会渲染成「请处理以下内容：STOP_LOOP」原样发给模型——既没跳过、提示词也被污染。这恰恰是典型场景里最自然的配置方式。

项目处于开发期、无兼容性约束，因此本方案直接修正该行为：**`quartet_set` 传入空值时就存空字符串**。由此：

- 跳过判定不需要任何哨兵字面值参与，只看渲染结果本身（§2.1 的两条规则：trim 为空、或单个未解析占位符）；
- `STOP_LOOP` 字面值回归唯一语义——Shell 控制文件的整行停循环指令；提示词正文中无论怎样出现这几个字都与跳过无关；
- 混合模板 + 空变量渲染出「固定正文 + 空串」，照常执行且无污染（见 §1 判定口径说明）。

### 2.3 进度记账：从分母扣除，而非记一条「跳过结果」

两种做法对比：

- ❌ 记一条「已跳过」的成功结果，完成数 +1：聊天流 / 结果列表里仍会出现无意义条目，会话计划也无法收缩。
- ✅ **从分母扣除**：跳过时总步数减一，并把跳过的步骤路径记入一个随任务持久化的「已跳过路径集合」。完成数、失败数都不动，进度条按缩小后的分母正常走满。

选择后者。复用现有「组提前退出时回填分母并推送」的机制：跳过时通过同一个进度更新事件把新的总步数和已跳过路径集合实时推给前端；页面刷新 / 事后查看时从持久化的任务状态中直接还原，不会被重新膨胀回静态值。

「已跳过路径集合」的语义约定：

- **粒度精确到重复槽位**：集合记录被跳过的叶子槽位（步骤路径含重复序号），不是步骤节点。同一步骤的不同重复槽位可能一个跳过、一个执行，必须分别记录。
- **路径身份跨端统一**：已跳过集合、进度更新事件、任务终态快照、查询接口、以及前端静态展开出的叶子路径，必须使用**同一种叶子槽位标识**，保证四端可直接比较。该标识须精确到重复槽位——包含从根到叶子路径上每一层的 group 迭代序号与 step 重复序号。注意它与分母回填映射（`groupActualIterations` / `groupActualLeafCounts`）的**路径粒度不同**：后两者以 **group 节点路径**为 key（只到 group 节点位置，不含 group 迭代序号、不含 step 重复序号），用于按组收缩计划；而已跳过集合以**叶子槽位路径**为 key（含每层迭代序号与重复序号），用于剔除单个槽位。二者可以**共享同一种路径序列化风格**（数组 / 拼接字符串等），但**粒度不可混用**。具体序列化形式留给实现，规则须一致。
- **幂等去重**：同一槽位至多记一次，分母也只对它扣一次。崩溃后重放、或 Continue 重入同一槽位时，不得重复计数、不得对分母二次扣减。
- **贯穿全生命周期**：运行中的进度更新事件、任务终态快照、以及任务查询接口返回的进度，三者都必须携带这个集合。只在运行中事件里带、终态 / 查询接口不带，会让刷新或历史查看时计划重新膨胀回静态值。

### 2.4 会话计划收缩

前端的会话 / 步骤计划由流程树静态展开得出。现已有一路动态裁剪输入——组提前退出的实际迭代数 / 实际叶子数（`groupActualIterations` / `groupActualLeafCounts`）；本方案再增加一路：已跳过路径集合。两路裁剪必须按固定顺序应用，且与后端「实际执行 + 已回填」口径一致，否则同一 group 内「前面有跳过、后面又 STOP」时前后端计划会错位。

**关键约定：组提前退出裁剪用的是「已消耗槽位前缀长度」，而非「实际执行槽位数」。** 组裁剪通过保留组内静态展开的前 N 个叶子来收缩计划（前缀裁剪），因此这个 N 必须等于 STOP 边界之前**已消耗的全部槽位**——即「实际执行槽位 + 已跳过槽位」之和，而不是仅「实际执行槽位」。否则当被跳过的槽位落在 STOP 边界之前的前缀内时，前缀会被截短，把本该保留的后续实际执行槽位裁掉、反而保留被跳过的槽位，导致前后端计划错位。前缀裁剪保留这段「已消耗前缀」后，再由第 3 步把其中的跳过叶子过滤掉，剩下的恰好是真实执行序列。

这意味着后端在组提前退出时写入 `groupActualLeafCounts` 的值，必须从现状的「实际执行槽位数」改为「实际执行 + 已跳过」之和；执行器须分别累计两个计数并随嵌套层级向上汇总。

计划计算顺序固定为：

1. 静态展开全部叶子槽位；
2. 应用组提前退出裁剪：按 `groupActualIterations` 收缩迭代数，按 `groupActualLeafCounts`（= STOP 边界前已消耗槽位前缀长度，含实际执行与已跳过）做前缀裁剪，保留各组的已消耗前缀；
3. 过滤掉已跳过路径集合中的叶子；
4. 在收缩后的叶子序列上，按现有规则（新会话边界、会话存续）分配会话。

效果：

- 只含被跳过叶子的会话整体消失，总会话数相应减少；
- 跳过步骤前后的步骤归属会话的规则与后端实际执行一致（后端跳过时同样不消耗 / 不重置会话指针）；
- 组裁剪先于跳过过滤，且组裁剪用的是「已消耗槽位前缀长度」（实际执行 + 已跳过）作为前缀边界，因此跳过叶子始终落在被保留的前缀内、再由跳过过滤剔除；不会出现「前缀太短把后续实际执行槽位裁掉、却保留了跳过槽位」的错位。

### 2.5 跳过时的「当前路径」推进

「当前路径」是进度里标记「现在跑到哪一步」的指针，前端据它在收缩后的会话计划里定位「Session X / Y · Step M / N」。真实执行的步骤会在轮次开始、结果保存两处自然写入它；而跳过步骤不产生轮次，因此跳过分支必须显式接管，否则当前路径会停在被跳过的路径或上一步旧路径上——前端把跳过叶子过滤掉后，会定位不到当前路径而回退到旧位置或显示无效计数。

规则：

- **跳过后把当前路径推进到下一个待执行叶子槽位**：使其指向恢复点新指向的下一步（与恢复点推进保持同一目标），而不是停留在被跳过的槽位上。
- **没有下一个待执行叶子时清空当前路径**：尾部步骤被跳过、或全部步骤被跳过导致后面再无可执行槽位时，当前路径置空。配合 §5 边界3「全部跳过、总步数为 0」按完成态走满，空当前路径不再尝试定位。
- **当前路径与其余跳过记账同写**：当前路径的推进必须与总步数扣减、已跳过集合、恢复点推进合并为**同一次持久化**（见 §3 跳过分支）。若当前路径单独落盘而恢复点没有，崩溃后 Continue 的兜底逻辑（从当前路径推算下一步）会从「下一步」再往后推一格，静默漏跑一个真实步骤。
- **进度更新事件携带当前路径**：跳过推送的进度更新事件除新总步数、已跳过集合外，一并带上更新后的当前路径，运行中页面据此实时重定位；任务终态快照与查询接口返回的进度同样反映这个推进后的当前路径。
- **前端降级**：前端定位时，若当前路径**非空**但落在已被过滤掉的跳过叶子上、或无法在收缩后的计划里命中，则降级到「按已完成 / 总步数」的全局计数展示，不显示错位的会话 / 步骤定位。当前路径为空（任务未开始 / 全部完成）维持现状展示。

## 3. 执行逻辑

对 Loop 模式下每个即将执行的 prompt 步骤：

1. 注入每轮内置变量，对提示词做变量替换。
2. 替换结果（去除空白后）非空、且不是单个未解析的 `{{变量}}` 占位符 → 按现状正常执行，零变化。
3. 替换结果为空、或恰好是单个未解析占位符（§2.1 两条规则）→ 跳过分支：
   - 不创建会话、不发任何轮次事件；记一条 INFO 日志（步骤路径 + 命中的跳过规则）；
   - **四项状态合并为一次持久化**，避免崩溃窗口产生不一致：总步数减一、步骤路径加入已跳过集合、恢复点推进到下一步骤、当前路径推进（规则见 §2.5）；
   - 幂等保护：若该槽位已在已跳过集合中（理论上不可达，防御崩溃重放），只推进指针、不再扣减分母；
   - 向已连接客户端推送进度更新事件（新总步数 + 已跳过集合 + 更新后的当前路径），前端实时刷新进度条与会话计划；
   - 会话指针保持不变（上一步骤的会话留给后续步骤按现有规则复用或重建）；跳过的步骤即使配置为「每轮新会话」，也不触发任何会话重置——它根本没运行；
   - 照常检查「步骤后边界」：优雅停止请求在跳过步骤的边界同样生效。
   - **持久化失败处理**：上述合并写入失败时，沿用现有进度持久化的尽力而为策略——记入持久化警告（不静默吞掉错误），内存继续推进；恢复点尚未落盘的情况下，进程重启 / Continue 会在该步骤的恢复点按 §2.1 重新注入变量并重判，变量仍为空则再次跳过自愈，变量已变则照常执行。即跳过分支不引入比「正常步骤推进恢复点」更强的失败语义。
4. 步骤重复次数大于 1 时，每个重复槽位**独立渲染、独立判定、独立记录**：每个槽位执行前都会注入 `_current_path` / `_current_time` / `_last_assistant_msg` 等每轮变量，即使模板原文相同，渲染结果也可能不同。因此不能因为模板文本相同就对一个槽位判一次、批量套用到其余槽位；必须逐槽渲染、逐槽判定是否跳过、逐槽扣减分母并记入已跳过集合。

### 3.1 执行步骤与状态

> 状态标注：已完成 = 已实现并通过构建与既有测试。

1. **后端进度模型增加已跳过路径集合**（粒度到重复槽位、幂等去重、随任务持久化、深拷贝覆盖）——已完成。
2. **`quartet_set` 空值行为修正**：传入空值时存空字符串，不再改写为 `STOP_LOOP`（§2.2）——已完成。
3. **prompt 步骤在创建会话之前完成每轮变量注入 + 变量替换 + 空 / 单占位符判定**（把判定时机提前到会话创建之前）——已完成。
4. **跳过分支的原子持久化**：总步数减一 + 加入已跳过集合 + 恢复点推进 + 当前路径推进，四者合并为一次写入——已完成。
5. **跳过时推送进度更新事件**（复用 `progress_total_updated` 事件，payload 扩展已跳过集合与当前路径）——已完成。
6. **组提前退出回填与跳过的口径对齐**：执行器分别累计「实际执行」与「已跳过」两个槽位计数并随嵌套层级向上汇总；跳过扣减计入「已回填」侧避免二次扣减；`groupActualLeafCounts` 写入值改为「实际执行 + 已跳过」之和（§2.4 关键约定）——已完成。
7. **Continue / 进程重启恢复对齐**：恢复点之前的槽位按持久化的已跳过集合分两侧对齐——已跳过的计入「已回填」侧，其余计入「实际执行」侧；跳过状态只从持久化集合读取、不按当前变量值重算——已完成。
8. **配置编辑（非运行态整体替换）的进度核对扩展**：结构变更时清空已跳过集合（与组回填展示映射同命运，分母同时被重算回新静态值，两者同步失效避免错位）；纯字段编辑（结构不变）时已跳过集合与扣减后的分母原样保留（§4.5）——已完成。
9. **任务终态快照与查询接口返回的进度携带已跳过集合与当前路径**——已完成（集合作为进度模型字段随任务持久化与查询自动携带，已验证进度经查询接口 / 终态持久化原样携带）。
10. **前端进度与 session plan 支持已跳过集合**（按 §2.4 固定顺序裁剪、消费扩展后的进度事件、按 §2.5 处理当前路径降级）——已完成。
11. **前端处理 `totalSteps = 0` 的完成态展示**：任务 Completed 且总步数为 0 时按 100% 展示（当前逻辑 `totalSteps > 0 ? ... : 0` 会卡在 0%），避免 NaN / 除零 / 0% 卡住——已完成。
12. **前端展示累计跳过步数**：进度区显示「已跳过 N 步」（数据即已跳过集合的大小，零额外接口）——已完成。
13. **更新执行器中「禁止静默短路」约束的说明**，注明空提示词跳过路径是经过记账修正的例外——已完成。

## 4. 与现有机制的协同

### 4.1 组提前退出的分母回填

组因 STOP_LOOP / 评估器停止提前退出时，会按「应跑槽位 − 实际执行 − 已回填」计算分母回填量。这里的关键是跳过槽位落在哪一侧：

- 跳过槽位**不计入「实际执行」**：它没有真正运行。
- 跳过槽位的扣减**计入所在组的「已回填」**：跳过当时已经把总步数减过一次。
- 因此组提前退出再次回填时，公式里的「已回填」必须包含本组内已发生的跳过扣减，否则「应跑槽位」仍把这些槽位算在内、而它们既不在「实际执行」也不在「已回填」，会被**二次扣减**，导致分母偏小、进度条提前到顶。
- **嵌套组同样成立**：内层组的跳过扣减要随递归向上汇总到外层组的「已回填」，外层组回填时才不会把内层已扣过的槽位再扣一遍。

一句话：跳过的分母扣减只发生一次，且永远归在「已回填」侧并逐层上报。

注意「已回填」与「已跳过」对 `groupActualLeafCounts` 的贡献不同：回填量是被裁掉的槽位（不进前缀），跳过槽位是已消耗的槽位（进前缀、再被过滤），见 §2.4 关键约定。

### 4.2 Stop → Continue 与进程重启

- 恢复点之前的槽位在 Continue 时会被记为「已消耗」以对齐分母数学。引入跳过后这些槽位不再等价，必须分两侧对齐：
  - 恢复点之前**真实执行过**的槽位：计入「实际执行」侧。
  - 恢复点之前**已跳过**的槽位：计入「已回填」侧，与首次运行的记账口径一致。
- **跳过状态只来自持久化集合，绝不重算**：恢复（Continue / 重启）时不重新渲染恢复点之前的提示词、不按当前变量值重新推断历史是否跳过——变量值在中断后可能已变，重算会得出与首次运行不同的结论。哪些历史槽位被跳过，唯一依据是持久化的已跳过路径集合。
- **恢复点恰好指向一个「将被跳过」的槽位**是正常情形（首次运行时该槽位的合并写入未落盘）：Continue 重入该槽位时按 §2.1 重新注入变量并重判——变量仍为空则再次跳过（幂等，集合里没有它所以不算重复扣减），变量已变则照常执行。
- 总步数与已跳过集合均随任务持久化，重启恢复后不重算静态展开值，进度显示与中断前一致。

### 4.3 「禁止静默短路」约束的关系

执行器中现存约束：prompt 变量不得用来悄悄跳过模型执行，否则分母虚高、轮次事件开闭不配对。该约束针对的是「跳过执行但记账照旧」；本方案跳过时同步修正分母、且完全不开启轮次（不存在开了不关的事件对），不触碰该约束保护的两个不变量。实现时更新该处说明，注明空提示词跳过路径是经过记账修正的例外。

### 4.4 与顶层 STOP / workflow stop 的关系（范围声明）

顶层步骤触发 STOP_LOOP / STOP_WORKFLOW 时，后端走 workflow 级回填，仅把总步数收缩到实际完成 / 失败数，不产出 root 级的前端 plan 裁剪输入（没有 group 那样的实际叶子数映射）。这意味着发生顶层停止时，前端会话计划的后缀 leaf 收缩本来就不完整——这是**顶层 stop 既有的限制，与本方案正交**：引入空提示词跳过既未制造、也未加重它。

因此本方案明确**不处理顶层 stop 的会话计划后缀收缩**，只保证：

- 跳过自身的分母扣减、已跳过集合、计划裁剪在顶层停止前后都自洽（跳过叶子照常从计划过滤）；
- 顶层停止时总步数仍按 workflow 回填正确收缩，进度条照常走满。

顶层 stop 的会话计划后缀收缩若要做，是一个独立改动（如引入 workflow/root 级实际叶子数，或把整个 flow 视为虚拟 root group 统一走组裁剪），不在本方案范围。

### 4.5 与配置编辑的协同

非运行态的整体替换配置会对进度做核对（reconcile），已跳过集合必须纳入同一套规则，否则会出现「分母被重算回静态值、集合却还在过滤叶子」的前后端错位：

- **结构变更**：总步数会被重算回新流程的静态值——跳过扣减随之被撤销，已跳过集合的路径 key 也可能不再指向原步骤。因此结构变更时**清空已跳过集合**，与现有的组回填展示映射（`groupActualIterations` / `groupActualLeafCounts`）同命运。被清空集合的历史跳过槽位等同「未完成」，编辑后 Continue 会重新到达并按 §2.1 重判——这是期望行为（编辑结构往往意味着用户想重跑）。
- **纯字段编辑（结构不变）**：所有路径仍然有效，**已跳过集合与扣减后的分母都原样保留**——与组回填映射的现有保留逻辑一致。否则一个已完成且含跳过的任务，仅仅改个提示词文案就会让进度条从 100% 回退。
- 结构变更后重锚恢复点的现有逻辑（指向第一个没有成功结果的步骤）无需感知跳过：被清空集合的槽位本就该重判，重锚到它是自洽的。
- 运行中的字段编辑不允许改结构、不允许改变量，对跳过记账无影响；被编辑的提示词文案对**尚未执行**的槽位生效，每个槽位执行前才渲染判定（§3 第 4 条），口径天然一致。

## 5. 边界条件

1. **引用未定义变量**：
   - 整条提示词**恰好只是一个** `{{变量}}` 占位符、变量未定义（占位符原样保留）→ 跳过（§2.1 规则 2）。典型场景的首轮（Shell 尚未设置变量）即落在这里。
   - 含固定正文、或由多个占位符拼接 → 占位符原样保留、整体非空，照常执行——固定正文表明用户有意发送内容，多变量拼接无法区分「全部无事可做」与「漏配了其中一个」，都不替用户吞掉。
2. **提示词正文包含 `STOP_LOOP` 字样**：与跳过完全无关（§2.2 之后该字面值只属于 Shell 控制文件的整行指令），照常执行。模板静态为空白本就被配置校验拦截，不存在「恒久跳过」的配置。
3. **全部步骤都被跳过、总步数减到 0**：不依赖「典型配置里 Shell 步骤始终计入分母」这一习惯——纯 prompt 且全部被跳过时总步数确实可能减到 0。此时规则明确为：
   - 任务正常以 Completed 结束，不视为失败；
   - 完成数、失败数均为 0；
   - 进度展示视为「已完成」（按 0/0 走满），不得出现 NaN、除零或卡住；
   - 会话计划为空时不展示任何「Session X / Y · Step M / N」，整块进度区按空计划渲染。
4. **被跳过的「每轮新会话」步骤之后是「复用会话」步骤**：后者执行时按现有规则回落到自建会话；前端剔除跳过叶子后按同样规则重算会话归属，两端一致。
5. **评估器 / Shell 步骤**：不参与跳过判定。评估器提示词替换后即使为空也照常执行（由其保守判停协议兜底）；Shell 脚本内容为空本就由配置校验拦截。
6. **跳过步骤上的优雅停止**：「步骤后停止」请求在跳过步骤的边界一样被消费，行为与真实执行过的步骤一致。
7. **混合模板 + 空变量**：「固定正文 + {{空变量}}」渲染为「固定正文」，非空、照常执行（§1 判定口径说明）。`quartet_set` 修正后（§2.2）不会再出现固定正文拼上 `STOP_LOOP` 字面值的污染。

## 6. 前端展示

- 进度条与「N / M」计数基于扣减后的分母，跳过不计入完成数与失败数。
- 进度区展示累计「已跳过 N 步」（N = 已跳过集合大小；N 为 0 时不展示该行）。
- `totalSteps = 0`（全部步骤被跳过）时，Completed 态按 100% 展示，不出现 NaN / 除零 / 卡 0%。
- 「Session X / Y · Step M / N」基于剔除跳过叶子后的会话计划；当前路径非空但落在已被过滤的跳过叶子上或无法命中时，按 §2.5 降级为全局「N / M」计数。
- 聊天流中跳过的步骤无任何消息（设计如此：本轮无事可做，不制造噪音；执行侧痕迹见后端日志与跳过计数）。
- 进度更新事件实时驱动运行中页面；刷新 / 历史查看从持久化状态还原，两条路径显示一致。
