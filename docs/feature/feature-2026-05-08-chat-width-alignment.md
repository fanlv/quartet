# 聊天页消息区与输入框宽度对齐 —— 实施方案

> 所属项目：Quartet Web
> 状态：已选型（方案 B），准备实施
> 纯文字方案，不含实现代码。

---

## 一、背景与目标

### 现象

在 `JobChat` 聊天页上，消息列表（MessageItem 所在的可滚动区域）与底部输入框（ChatInput）虽然都在同一个居中容器（`chatbot-main`，最大宽度 1360）内，但它们的左右边界并不一致：

- 消息区右侧比输入框右侧更靠内，视觉上消息气泡"缩"进去一点，输入框"外扩"一点。
- 差距来源是两边的右内边距不一致，以及消息区的滚动条占用了额外宽度。

### 目标

1. 让**消息内容的可视宽度**（尤其是右边界）与**底部输入框的可视宽度**保持一致 —— 从顶部的助手气泡/文字块到底部输入框，整列视觉右缘对齐成同一条线。
2. 滚动条**相对位置保持不变**：仍然出现在聊天主区的右边缘，滚动体验与现在一致；允许滚动条与消息内容的右边缘在视觉上"贴边"甚至轻微覆盖（用户已明确接受）。
3. 左边界、现有外部布局（侧栏、Header、Loop 布局）**不受影响**。
4. 响应式（移动端窄屏、平板断点）下依然保持两者宽度一致；消息区和输入框的断点规则要成套匹配，避免只改其中一个。

### 非目标

- 不调整 `chatbot-main` 的最大宽度（仍为 1360）。
- 不重构消息列表的滚动、吸底、自动滚到底部逻辑。
- 不改变用户气泡 70% 宽度上限等气泡级别的样式约束。
- 不动 Loop 模式下侧栏、FileBrowser 等其他面板的布局。

## 二、现状梳理

| 维度 | 现状 |
|---|---|
| 容器层级 | `chatbot-container` → `chatbot-body` → `chatbot-main` → [`MessageList`, `ChatInput`] |
| 滚动容器 | `MessageList` 内部的 `.message-list` 自己滚动，滚动条在它的右边 |
| 消息区左右内边距（默认） | 左 24、右 8；右侧还要再减去 6 的滚动条宽度 |
| 输入框左右内边距（默认） | 左 24、右 6 |
| 输入框响应式 | @1180、@1024、@768 各有一档，左右内边距分别为 24/24、16/16、12/12 |
| 消息区响应式 | 仅 @768 一档：左 8、右 8 |
| 吸底 | `ChatInput` 外层设为 sticky 贴底，相对于 `chatbot-main` |

关键事实：**滚动条现在属于消息区本身**，因此它占用的 6px 只会让消息内容变窄，而不会影响输入框。输入框的右边距直接等于滚动条宽度（6），目的是让输入框的右缘与"消息区滚动条的左缘"视觉对齐 —— 但这要求消息区右内边距为 0，而现在是 8，于是默认宽屏差了 8px。

此外，消息区没有覆盖到输入框所有响应式断点，导致在 1180 / 1024 这两档也会出现错位（现象与默认态略有不同，但属于同一根因）。

## 三、方案（方案 B）

### 思路

**不改动滚动层级**：`.message-list` 继续作为独立滚动容器，滚动条继续在它的右边。只做两件事：

1. **让出滚动条占用的宽度**：把 `.message-list` 的右内边距调整为 `ChatInput 右内边距 − 滚动条宽度`，让消息内容的右缘与 ChatInput 的右缘对齐到同一条垂直线。允许滚动条视觉上贴住消息内容的右缘（用户已确认接受）。
2. **稳定滚动条槽位**：启用稳定的滚动条占位（scrollbar gutter 始终预留），这样即使消息数量少、滚动条不可见时，右侧依然保留同样的槽位宽度，不会出现"有滚动条时对齐、没有滚动条时消息比输入框更靠右"的抖动。

### 响应式断点处理

消息区的响应式规则与输入框成套对齐，保证所有断点下右缘都重合：

| 断点 | 输入框左右内边距 | 消息区左右内边距（目标） |
|---|---|---|
| 默认（宽屏） | 左 24、右 6 | 左 24、右 0（滚动条槽位补足 6） |
| ≤1180（宽窗平板） | 左 24、右 24 | 左 24、右 18（补足 6） |
| ≤1024（平板） | 左 16、右 16 | 左 16、右 10（补足 6） |
| ≤768（手机） | 左 12、右 12 | 左 12、右 6（补足 6） |

补足公式：消息区右内边距 = 输入框右内边距 − 6（滚动条槽位宽度）。

### 改动范围

- 仅 CSS 改动，集中在 `MessageList.css` 的 `.message-list` 规则（默认 + 各响应式断点）。
- 顺手在文件头注释一句"左右内边距与 `ChatInput` 相应断点成套匹配"，防止后续只改其中一个又错位。
- `ChatInput.css` 不改。
- 不涉及任何 TSX 逻辑改动：滚动容器身份、自动滚到底部、用户上滑检测、新消息追逐等全部不动。

## 四、影响与风险

### 不受影响

- `MessageList.tsx` 的滚动事件监听、`scrollToBottom`、`userScrolledUpRef`、切会话落底、流式追逐底部等逻辑 —— 全部基于同一个滚动容器，容器没变，行为不变。
- `JobChat.tsx` 父布局、Loop 模式侧栏、`ChatInput` 吸底、欢迎页、空态、Loading 指示器。
- 用户气泡 70% 宽度、助手气泡、Markdown 渲染、代码块、表格等气泡内部样式。

### 需要接受的视觉取舍

- 消息内容会紧贴滚动条，长代码块/表格的右缘可能会被滚动条盖住一条细边。用户已确认接受（"滚动条可以在 MessageItem 边缘上面"）。

### 需要注意的边界

- 依赖现代浏览器的稳定滚动条槽位特性；主流浏览器（近两年的 Chrome / Firefox / Safari）均已支持。老版本浏览器上可能退化为原行为（右侧槽位抖动），非目标用户场景，不特殊处理。
- 后续若在消息列表里引入虚拟滚动、自定义覆盖式滚动条等更大改动，再按当时的上下文重新评估（可能升级为将滚动能力上提到 `chatbot-main` 的更大重构）。

## 五、验收标准

1. 在默认宽屏、≤1180、≤1024、≤768 四档宽度下，消息气泡群的右边缘与 ChatInput 右边缘在视觉上对齐成同一条垂直线。
2. 左边缘同样对齐（在 1180/1024/768 三档也成立）。
3. 滚动条依然出现在聊天主区的右边缘，用户上下滚动体验与现在一致：
   - 向上翻历史消息顺畅。
   - 底部追逐（新消息自动吸底）仍然生效。
   - 用户主动上滑后，不会被新消息强拉回底部。
4. 消息少、滚动条不可见时，右侧依然保留一致的槽位宽度，右缘不抖动。
5. Loop 模式（含侧栏打开/关闭）下布局不破。
6. 欢迎页、空态、Loading 提示、Sticky 到底部的输入框都正常显示，没有出现双滚动条、叠加阴影、遮挡等异常。
