# 技术方案：Graph 长循环存储治理（对齐 Loop 的按 session 存储模型）

## 背景

一个运行了 9 小时、循环几十轮的 Graph 工作流 Job，打开页面要卡 15–20 秒。实测定位到根因：

- 该 run 的 `events.jsonl` 已涨到 **307MB / 10 万行**；`GetRunStatus`（`GET /graph/run/{id}`）一次性把全部事件读出并塞进响应体，单次响应 **313MB、耗时 5–19 秒**，前端打开页面期间还重复拉了 8 次。
- 307MB 里几乎全是冗余，分两块：
  1. **逐字符流式事件**（`agentMessageDelta` / `agentThoughtDelta` / `agentTool*`，约 35MB）：这是 Agent 节点的对话流。但 Graph 的 Agent 节点和 Loop 用的是同一套 runner，对话**本来就已经完整持久化在各自 session 的 `messages.jsonl` 里**（实测 30 个 session、各约 50KB）。事件流里的逐字符 delta 等于把同一份对话又存了第二遍。
  2. **生命周期事件内嵌的全量 progress 快照**（`instanceStarted` / `instanceCompleted` / `instanceSkipped` / `loopIteration`，约 184MB）：每发生一次节点生命周期事件，就把当前全量 progress（含上百个 instance 的状态）整份写进该事件。轮数越多 progress 越大、每个新事件越大，文件随轮数**二次方膨胀**。这份 progress 在 `progress.json` 里已有权威副本。
- 前端拿到 307MB 的 `events` 数组后，**唯一用途是取它的长度**（当作 SSE 续传游标），整个数组随即丢弃。

对比同样支持多轮循环的 **Loop 引擎**，它不存在这个问题，差异就在存储模型：

| | Loop 模式 | Graph 模式（现状） |
|---|---|---|
| 对话历史 | 各 session 的 `messages.jsonl`（分散） | 同样走 session `messages.jsonl`（分散） |
| 实时流式事件 | 纯内存 ring buffer，推完即 GC，**不落盘** | 全量写入 `events.jsonl`，逐字符永久堆积 |
| 每轮摘要 | `JobProgress.Results`，仅轻量字段 | 每个事件内嵌全量 progress 快照 |
| 历史加载 | 按 session 懒加载（各约 50KB） | 一次性返回全量 events（307MB） |

核心差异一句话：**Loop 的实时事件是“用完即弃”的内存流，Graph 把每一个流式事件都永久写进了一个聚合大文件。**

不解决的影响：循环轮数越多，文件越大、加载越慢，最终页面无法打开、磁盘被单个 run 吃掉数百 MB，且 SSE 续传与 resume 也会被拖慢。

## 目标

让 Graph 在几十到上百轮循环下，run 的持久化体积与加载耗时保持平稳（不随轮数二次方增长），页面打开恢复到亚秒级。手段是把 Graph 的存储模型对齐 Loop：**权威对话归 session、实时流式事件不落盘、结构化摘要瘦身。**

## 范围

**做**：
- 重新划分 Graph run 的三类数据归属，按归属决定是否落盘。
- 全量状态接口不再返回事件数组。
- 生命周期事件不再内嵌全量 progress 快照。
- 逐字符流式事件改为内存广播、不落盘；历史对话改为从 session 读取。
- instance / progress 瘦身，已完成的旧迭代从“热状态”归档。
- 事件文件滚动上限兜底；前端去重重复请求。

**不做**：
- 不改 Graph 的执行语义（调度、分支、循环、会话血缘、resume 的业务规则均不变）。
- 不改 Agent 节点对话的存储位置（继续存 session `messages.jsonl`，本就正确）。
- 不动 Loop 引擎。
- 不做存量超大 run 的历史数据迁移（仅提供清理入口，见风险）。

## 方案设计

### 数据归属重划（总原则）

把 Graph run 的数据按“是否必须持久化”分三类，各归其位：

1. **权威对话历史**：已在 session `messages.jsonl`，不动。
2. **结构化执行结果**（每个 instance 跑完的摘要：状态、所属 session、起止时间、耗时、token、输出变量）：留在 `instances.json` / `progress.json`，但瘦身。
3. **实时流式事件**（逐字符 delta、工具流、节点生命周期播报）：改为内存流，只用于实时 SSE 推送，不落盘。断线重连与历史回看，靠“读 session 对话 + 读 progress 摘要”重建，而不是回放事件文件。

落盘的事件文件只保留**稀疏的结构性事件**（边解析、循环轮次推进、节点完成摘要、错误），用于 resume 和审计。这部分即便上百轮也只有几 MB。

### 第一层：止血（立刻把加载降到亚秒，改动小、零风险）

- **全量状态接口不再返回 events 数组**：`GetRunStatus` 不再读取全部事件，响应里用“事件计数”替代“事件数组”（前端只需要这个数当续传游标）。响应体从 313MB 降到几十 KB。
- **生命周期事件不再内嵌全量 progress 快照**：节点 started/completed/failed/skipped 等事件去掉随附的整份 progress。前端节点状态颜色改为只认 `progressUpdated` 事件加初始全量 progress（前端已是此机制）。事件文件从 307MB 砍到约 35MB。

### 第二层：根治（对齐 Loop，让流式事件不再落盘）

- **逐字符流式事件改为内存广播**：Agent 节点的 message/thought/tool 流只用于实时 SSE 推送，推完即弃，不再追加到事件文件。
- **历史对话改为按 session 加载**：前端打开某节点的对话时，直接走已有的“按 session 取消息”接口（Graph Agent 对话本就存在那里），与 Loop 完全一致，实测每个 session 仅约 50KB、20–30ms。
- **resume / 断线重连重建逻辑调整**：重连后不再依赖回放事件文件来补齐对话，改为从 session 对话与 progress 摘要重建当前视图；事件文件只供结构性事件的增量续传。

经此一层，事件文件从约 35MB 再降到几 MB，且增速从“逐字符”降到“每节点几条”，几百轮也能撑住。

### 第三层：摘要瘦身与归档

- **progress / instances 瘦身**：每个 instance 在 progress 里不再保留全量可见变量快照（前端不读），只保留状态、session、起止时间、输出摘要。
- **旧迭代归档**：已完成的历史迭代 instance 从“热 progress”移出，归档到按需加载的位置，对齐 Loop 的 `Results` 只存轻量摘要的做法，避免热状态随轮数线性变大并每次全量重写。

### 第四层：防御性兜底

- **事件文件滚动上限**：落盘事件文件超过设定体积时，自动滚动并丢弃旧的纯展示类事件（结构性事件保留），作为“即使有遗漏也不再爆几百 MB”的安全网。
- **前端合并重复请求**：合并两处各自独立触发的全量状态拉取，避免开场并发多次大请求。

### 落地顺序

- 第一层：立即解决当前已膨胀 job 的打开卡顿。
- 第二层：根治膨胀，是“几十上百轮不再复发”的关键；需同步调整前端历史加载与 resume 重连逻辑。
- 第三、四层：收尾瘦身与防御，防止边角场景复发。

第一层加第二层一起做，才算真正根治：第一层只是让已经 307MB 的 run 能打开，第二层才能保证以后几百轮的 run 不再产生 307MB。

## 风险

- **断线重连/历史回看的语义变化**：从“回放事件文件”改为“读 session 对话 + progress 摘要”，需保证两条路径渲染出的对话与节点状态一致，避免重连后丢消息或状态错位。这是第二层的主要验证点，需重点测多轮循环下的重连。
- **存量超大 run**：已经产生的几百 MB `events.jsonl` 不会被本方案自动缩小。提供按 run 的清理/删除入口即可（单用户、本机场景，可接受手动清理）；新逻辑只保证新 run 不再膨胀。
- **resume 依赖的事件**：需确认 resume 真正依赖的是持久化的结构性事件与状态快照，而非逐字符流式事件；裁剪流式事件落盘前必须核对 resume 不读这些事件。

## 可观测性

- 事件落盘处按事件类别记录写入量，便于确认流式事件确实不再落盘。
- 全量状态接口记录响应体大小与耗时，作为回归基线（目标从百 MB/秒级降到 KB/毫秒级）。
- 事件文件滚动触发时打日志（run、触发体积、丢弃事件数）。
- 重连重建路径记录来源（session 对话 + progress），便于排查重连一致性问题。

## 执行步骤

1. **接口瘦身（第一层-1）**：全量状态接口去掉事件数组、改返回事件计数；前端续传游标改用计数。
2. **生命周期事件去快照（第一层-2）**：节点生命周期事件不再内嵌全量 progress；前端节点状态色改为只认 progress 更新事件加初始 progress。
3. **流式事件不落盘（第二层-1）**：Agent 流式 delta/tool 事件改为仅内存广播，不写事件文件。
4. **历史对话按 session 加载（第二层-2）**：前端节点对话历史改走按 session 取消息接口。
5. **重连/resume 重建调整（第二层-3）**：重连后从 session 对话与 progress 摘要重建视图；核对并保留 resume 所需的结构性事件。
6. **progress/instances 瘦身（第三层-1）**：热状态去掉全量可见变量快照，只留摘要字段。
7. **旧迭代归档（第三层-2）**：已完成迭代 instance 移出热状态、按需加载。
8. **滚动上限兜底（第四层-1）**：事件文件超限滚动、保留结构性事件。
9. **前端请求去重（第四层-2）**：合并重复的全量状态拉取。

## 验收标准

- **加载性能**（用户手工测试）：用一个几十轮循环的 Graph run 打开 Chat 页，全量状态接口响应体降到 KB 级、打开恢复到亚秒级。
- **体积平稳**（用户手工测试）：连续跑上百轮循环，run 的持久化总体积不随轮数二次方增长，事件文件稳定在数 MB 内。
- **对话完整**（E2E）：多轮循环结束后，逐个打开各节点 session，历史对话完整、与运行时一致。
- **节点状态正确**（E2E）：运行中与刷新后，节点状态颜色、进度、循环轮次显示正确（不依赖事件文件内嵌快照）。
- **断线重连一致**（用户手工测试 + E2E）：运行中断开重连，对话与节点状态正确恢复，无丢失或重复。
- **resume 正常**（E2E）：失败/暂停/步骤后停止的多轮循环 run 能正确续跑，续跑后状态与对话一致。
- **滚动兜底生效**（单测）：事件文件超限时正确滚动并保留结构性事件。
- **存量 run 可清理**（用户手工测试）：已膨胀的历史 run 可通过删除入口清理。
