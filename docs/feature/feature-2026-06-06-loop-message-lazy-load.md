# Loop 模式消息加载：从「全量预加载」改为「激活优先 + 空闲预取」

- 创建日期：2026-06-06
- 作者：Sophie
- 相关文件：`web/src/hooks/useJobChat.ts`

## 背景

进入 Loop 模式的 Job 页面时，前端原先会对该 Job 下**每一个 session** 都各拉取一次完整历史消息。
当一个 Loop Job 跑了很多轮（每轮一个 session）时，这会带来三类开销：

1. 一次性发出 N 个历史请求；
2. 后端对每个 session 全量读盘并重新计算 token；
3. 前端内存里堆放所有 session 的消息。

结果是 session 越多，首屏与切换越被拖慢。而实际上前端已经具备懒加载所需的全部基础设施：
有「已加载 session 集合」的记录、有「切到未加载 session 时自动补加载」的机制、UI 也有
「正在加载该 session 消息」的占位提示。原实现只是主动选择了「全量预加载」。

## 方案

保留「激活 session 优先加载、首屏立即解除阻塞」，把「立即并发全量预加载其余 session」改为
**懒加载 + 浏览器空闲时低优先级预取**。

- **激活优先**：进入页面时只同步加载当前激活的 session（分享链接指定的、否则最后一个），
  加载完成即解除首屏阻塞，用户立刻能看到内容。
- **空闲预取**：其余 session 不再抢首屏资源，而是在浏览器空闲时段逐个、低优先级地预热进内存，
  以便后续切换 tab 顺滑。预取整体可被打断：一旦切换了 Job 或页面卸载，未完成的预取立即停止。
- **懒加载兜底**：若用户在预取尚未覆盖到某个 tab 前就主动点击它，沿用既有的「切换即按需加载」
  机制立即加载该 session，期间显示既有的加载占位；预取与按需加载之间不会重复拉取同一个 session。
- **失败可重试**：预取某个 session 失败不会中断整条预取链；该 session 会被标记为失败，
  用户切到它时会再次尝试加载。

## 断线 / 补洞路径统一

除初始进入页面外，还有两类「无实时流续传、需从磁盘补齐历史」的恢复场景：SSE 断点失效后的
磁盘重载，以及空闲看门狗触发的状态补洞。这两条路径原本也是全量加载所有 session。本次将它们
统一为与初始进入页面一致的「激活优先 + 空闲预取」行为，避免出现「初次进入是懒加载、断线恢复后
又变全量」的不一致。

其中非 Loop 的普通会话恢复路径保持原有全量加载：这类 Job 会话数量很少，且其 token 总量统计
依赖把全部会话历史一并加载，不适合改为懒加载。

## 不受影响的状态

以下与 Loop 展示相关的状态均不依赖「所有 session 的消息都已加载」，懒加载后仍然正确：

- **Token 总量**：Loop 模式下来自实时用量事件与每个 session 的运行结果汇总，不来自历史消息拉取。
- **会话 tab 列表 / 已结束会话标记**：来自 Job 自身的进度与状态元数据，与消息是否加载无关。
- **每个 session 的模型 / Agent 元信息**：切到尚未加载的 tab 时会有短暂空缺，待该 session 加载完成后
  自动补齐显示。
- **运行中新产生的 session**：通过实时流增量进入并自动跟随，消息也由实时事件追加，整条路径不经过
  历史拉取，不受本次改动影响。

## 验证

- `cd web && npm run build`（类型检查 + 构建）、`npm run lint` 通过。
- `make dev` 起真实链路，打开一个含多个 session 的 Loop Job：用浏览器网络面板确认进入页面时
  历史消息接口**只发 1 次**（激活 session），其余在浏览器空闲时才陆续补发，首屏不被阻塞。
- 在预取完成前主动点击一个尚未加载的历史 session tab：确认短暂显示加载占位后正确渲染，且该 tab 的
  模型 / Agent 元信息正确。
- 模拟断线恢复（触发 SSE 断点失效 / 空闲看门狗）：确认恢复后同样是激活 session 先出、其余空闲补齐，
  消息不丢、不重复。
- 运行中场景：Loop 正在跑时新产生的 session 通过实时流实时进入并自动跟随，行为不变。
