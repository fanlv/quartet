# Job 标题手动编辑 —— 功能方案

> 所属项目：Quartet
> 状态：设计
> 纯文字描述文档，不含实现代码。

---

## 一、目标

让用户在 Job 聊天页**手动修改 Job 的标题**，覆盖掉自动生成或初始消息衍生的标题。

使用场景：

- 自动生成的标题不够准确、偏题或太长，用户希望手工整理成一个更贴合自己记忆的名字。
- 基于模板启动的 Loop 任务，用户希望加一个可区分的后缀（比如"公司 A 调研"、"公司 B 调研"），方便在 Job List 中定位。
- 一次任务聊着聊着话题变了，用户想把标题改成更能反映当前实际内容的字眼。

范围约束：

- **仅限编辑标题本身**，不改 Job 的其它任何配置（mode、workdir、agent、LoopConfig.flow 等）。
- **只读分享页不出现入口**，接收方无权改名。
- 不做"自动重新触发 LLM 生成标题"之类的附加功能，这里只负责手动改名。
- 不做标题历史 / 多版本：标题只保留最新一次。

---

## 二、现状梳理

| 维度 | 现状 |
|---|---|
| 标题来源 | 首次发消息后异步调 LLM 生成；生成前展示首条用户消息截断文本或默认 `Quartet` / `Loop Task` |
| 标题展示 | Job 聊天页左上，头像右侧一行文字；超过 40 字符省略号截断 |
| 标题持久化 | `Job.Title`，与 Loop 场景下同步到 `LoopConfig.Variables[_job_title]` |
| 标题更新通道 | 后端已有 service 层 `UpdateTitle`，会持久化并 bump list 版本；自动生成流程成功后会广播一个标题更新的 Custom 事件，前端通过 SSE 接收后实时刷新 |
| HTTP 入口 | **无**：标题更新目前只发生在后端自动生成路径，没有对外的手动修改端点 |
| 只读分享页 | 订阅的是同一套事件流，天然会跟着刷新 |

结论：后端 service 和事件广播都已齐备，缺的只是"用户手动修改"这条路径的**对外端点**和**前端入口**。

## 三、方案

### 3.1 编辑入口与交互

- 在 Job 聊天页标题右侧常驻一个小的编辑图标按钮，与 Share / File Browser / Settings 等头部按钮沿用同一套尺寸、色板和 hover 风格，保持视觉统一。
- 仅在**非只读**且**已有 jobId** 的前提下显示；新建中、分享页面不显示。
- 点击后标题原地切换为可编辑输入框，自动聚焦并选中原内容；旁边出现保存 / 取消两个图标按钮。
- **Enter 保存**，**Esc 取消**，点击外部视为取消。
- 编辑中按钮区暂时代替标题位置，不做整行重排，避免头部高度抖动。
- 保存中展示 loading 状态；失败时**把后端返回的原始错误信息**显示出来（延续"错误全量展示"的原则）。

### 3.2 校验规则

- 输入值前后空白一律 trim。
- trim 后**必须非空**，空标题按钮 disabled，直接不让提交。
- 长度上限 **200 字符**（按用户可见字符而非字节计算），超长阻止提交并给出明确提示。
- 与旧标题相同（trim 后一致）则视为 no-op，不发请求，直接退出编辑态。

### 3.3 后端端点

- 新增一个**幂等的标题修改端点**：`PUT /api/v1/job/:jobId/title`，入参只含新标题一个字段。
- 行为：
  1. 基本校验（jobId 非空、标题 trim 后非空、长度不超限）不通过返回 400，错误原因原样带回前端。
  2. 校验通过后调用 service 层 `UpdateTitle`：标题持久化、`LoopConfig.Variables[_job_title]` 同步、`UpdatedAt` 刷新、list 版本号 bump。
  3. 广播一个**标题更新的 Custom 事件**（复用现有事件名与结构，即自动生成标题流程用的那条），让同一 Job 的其它订阅端（多标签页、分享页）也能实时刷新。
  4. Job 不存在返回 404；service 其它错误返回 500，错误信息透传。
- 不做 auth 之外的额外访问控制：当前是单用户本机场景，`CLAUDE.local.md` 已明确不考虑多用户权限问题。

### 3.4 前端本地联动

- 保存成功后：
  - 立刻用返回值刷新本页 `jobTitle` 状态，同时同步左上浏览器 `document.title`。
  - 把新标题 patch 进头部右上的 Job List 下拉，不必等轮询。
- 失败时：停留在编辑态，输入框不清空，错误文案就近展示。
- SSE 广播到达时仍正常处理（哪怕是自己触发的那一次），保证多端一致；幂等，不会引起闪动。

### 3.5 Loop 变量的同步

- Loop 模式下，`{{_job_title}}` 模板变量随着标题变化一并刷新（service 层 `UpdateTitle` 已经承担此职责，不额外在 handler 里做）。
- 正在运行中的一轮 Loop 不打断，下一次引用 `_job_title` 时自然取到新值。

### 3.6 只读 / 分享页行为

- 分享页不展示编辑按钮。
- 分享页仍订阅事件流，**标题变更会实时反映在分享页上**（与自动生成路径一致），这是刻意保留的行为 —— 改名是给所有看到这个 Job 的人看的同一块文字。
- 如果用户不希望别人看到最新标题，应通过停止分享解决，不在本方案覆盖范围。

## 四、与其它功能的关系

- 与**自动生成标题**共存：用户首次发消息后的自动生成依旧会触发一次；如果用户在自动生成前手动改过，后续自动生成**不会再回填覆盖**用户的手动结果。判断方式复用现有自动生成路径的"是否已有标题"前置条件。
- 与 **Job List 展示**一致：List 侧从 Job meta 读取 Title，标题变了 list 自然跟着变。
- 与 **Loop 配置面板**无直接耦合：面板里显示的标题只是镜像，不在本方案内做同步改造。

---

## 五、验收要点

- 打开任意一个已有 Job → 标题右侧能看到编辑按钮；新建未保存状态下不显示；只读分享页不显示。
- 点击编辑按钮 → 标题变成输入框，自动聚焦并选中；Enter 保存、Esc 取消、点击外部取消，行为一致。
- 保存空字符串 / 全空格 → 按钮 disabled 或阻止提交；长度超限阻止提交并有提示。
- 保存与旧值相同 → 不发请求，退出编辑态。
- 保存成功 → 头部标题、浏览器 `document.title`、右上 Job List 三处立即刷新；刷新页面后仍是新值。
- Loop 任务改名后，`{{_job_title}}` 在下一次被引用时拿到新值。
- 多标签页打开同一 Job：一侧改名，另一侧通过事件流自动更新。
- 分享页在源端改名后也会实时跟随更新。
- 后端校验失败或 service 异常 → 前端**看到真实错误信息**，编辑态不被清空。
- 自动生成路径与手动修改不会互相覆盖：用户手动改过之后，后续自动生成不会回填。

## 六、后续可扩展项（不在本期范围）

- **标题变更历史**：记录每一次手动 / 自动改名，做回放或撤销。
- **改名事件落盘到 user_input**：沿用"用户输入按天落盘"的窄口径，把手动改名作为一类 `kind`，与 Loop Start / 聊天消息混排。
- **Job List 行内改名**：不进入聊天页也能快速重命名。
- **多用户化后的权限控制**：只允许创建者改名。
