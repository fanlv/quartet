# SSE 断开后历史 Job 发消息重复显示旧回复

日期：2026-06-03

## 现象

在 SSE 已断开的情况下（典型是服务重启后、或页面长时间空闲后），进入一个历史 Job 发送消息，回复正常，但发送后会**立刻多显示一条之前已经出现过的旧回复**。被重复显示的内容形如：

```
[No content][No content][No content]襄阳今明两天天气如下……
```

刷新页面后这条重复消息依然存在（说明它已经被写进了磁盘历史，不是纯前端渲染问题）。

## 根因

这是 **coco（ACP 子进程后端）自身的问题**，与前端去重、也与 quartet 后端逻辑无关。

coco 子进程在新一轮 Run 开始、需要重新对齐会话上下文时（服务重启 / 长时间空闲后子进程被重建或重新加载会话），会把它会话记忆里**上一轮的 assistant 回复重新输出一遍**（回放 / echo）。这条回放消息有两个明显特征：

1. 内容以占位符 `[No content]` 开头（coco 把空内容块渲染成了字面量 `[No content]`，该字面量完全来自子进程，quartet 代码中不存在）；
2. 落盘时 `started_at == finished_at`（瞬时产生，没有真实的流式生成过程）。

quartet 的轮次构建逻辑把这条回放消息当成了本轮新产生的 assistant 消息：

- 给它分配了一个**全新的消息 ID**；
- 写入磁盘历史；
- 通过 SSE 推送给前端。

前端所有的消息去重都是按**消息 ID** 进行的。由于这条回放消息的 ID 是全新的，与历史里那条原始回复的 ID 不同，前端无法识别为重复，于是立刻多渲染了一条旧内容。磁盘历史里也因此多出一条重复消息。

### 为什么只在 SSE 断开 / 重启后出现

正常在线连续对话时，coco 子进程会话内存是连续的，不需要回放上一轮内容；只有当服务重启、或长时间空闲导致子进程被重建 / 重新加载会话时，新一轮 Run 才会触发这次回放，从而暴露问题。

### 与"消息消失"是两个独立问题

本仓库此前修复的"SSE 断开后发消息、消息消失"问题，原因是前端断线恢复路径用覆盖式写入丢弃了未确认的乐观消息（已修复）。本问题正相反——是**多**出一条旧消息，根因在 coco 子进程把历史回放当成了新消息发出。两者互相独立。

## 处理结论

**不再在 quartet 代码里做任何兼容处理。** 这是 coco 后端自身的 bug，应由 coco 修复（在 resume / 重建会话时不要把上一轮回复当成新的流式输出重新发出）。

quartet 此前曾在落盘前用启发式（`[No content]` 前缀 + 瞬时耗时）识别并丢弃这种回放消息，但该方案存在固有缺陷：

- 只能拦住落盘，拦不住流式上屏（echo 的 delta 在轮次构建早期就已经推给前端）；
- 纯时间 / 前缀启发式无法可靠区分回放与真实快回复，存在误伤真实新消息的风险。

因此已**移除全部相关兼容代码**（落盘前的 echo 识别与丢弃逻辑及其单测），把问题交还给 coco 修复。

## 影响范围

- 在 coco 修复前，该回放重复消息会重新出现（落盘 + 上屏），属已知问题。
- 仅影响使用 coco 后端的 ACP 路径；其它 ACP 后端与 eino 路径不受影响。
