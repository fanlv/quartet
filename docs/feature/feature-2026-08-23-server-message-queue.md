# 普通 Job 服务端消息队列与跨端排队界面方案

日期：2026-08-23

## 1. 概述

普通交互式 Job 正在执行时，Web 和 iOS 当前会把后续消息保存在各自页面的内存队列中。页面刷新、离开对话页或 App 进程结束后，尚未发送的消息会丢失；两个客户端也无法看到彼此排入的消息。Web 端目前还把多条排队消息以标签形式放在输入框内部，占用编辑空间，队列层级不清晰。

本功能把排队职责迁移到服务端：客户端提交消息后，由服务端原子决定立即执行或持久化排队；服务端按 Job 严格顺序自动发送。Web 与 iOS 读取同一份队列，支持逐条删除，并把队列展示为吸附在输入框上边缘的独立列表。

## 2. 目标

- 排队消息在 Web 刷新、iOS 页面重建和后端重启后仍可恢复。
- Web、iOS 和同一 Job 的其他已授权客户端看到一致的队列内容与顺序。
- 每次发送形成一条独立队列项，多次发送按服务端接收顺序逐条执行。
- 用户可以删除任何尚未被服务端领取执行的队列项。
- 用户主动停止当前执行时暂停后续队列，并可显式继续。
- 队列自动执行时延续现有对话上下文，不重置 ACP session。
- 排队区不占用文本编辑区域，并清楚区分“等待发送”和“已经进入对话”的消息。

## 3. 范围与原则

### 3.1 本期范围

- 仅支持普通交互式 Job。Graph Job 的节点讨论、工作流调度消息不进入本队列。
- 支持文本消息和已经上传到服务端的图片附件。
- 支持队列的提交、读取、自动执行、逐条删除和跨端同步。
- 队列是 Job 级共享数据，不按浏览器、设备或账号拆分；现有 RBAC 只控制读取与执行能力。

### 3.2 核心原则

1. **服务端是唯一事实来源**：客户端收到服务端确认后才显示为正式排队项。
2. **先入先出**：同一 Job 始终按服务端确认的顺序串行执行，不使用客户端时间决定顺序。
3. **发送与入队原子化**：客户端不先查询 Job 状态再选择接口；服务端在同一个提交动作中决定立即执行或排队。
4. **删除与领取互斥**：删除成功的消息绝不能再执行；已经被领取的消息不能再按“删除排队消息”处理。
5. **上下文连续**：队列执行复用现有会话与上下文，不因并发、失败或队列切换重置 ACP session。
6. **错误完整可见**：提交、同步、删除或自动执行失败时，Web 与 iOS 均展示服务端返回的完整错误。
7. **生命周期完整交接**：只有上一轮执行及其运行资源全部退出后，服务端才能领取下一条消息。
8. **用户停止优先**：用户主动停止代表暂时不希望继续执行，服务端不得立刻启动下一条排队消息。

## 4. 用户故事

### US-001：运行中继续发送并持久化排队

**用户故事：** 作为用户，我希望 Job 运行时继续发送消息，并由服务端保存，以便刷新或换设备后消息不会丢失。

**验收标准：**

- [ ] Job 空闲且没有既有排队项时，提交的消息立即开始执行。
- [ ] Job 正在执行或已经存在排队项时，提交的消息由服务端确认入队。
- [ ] 连续提交三条消息后，服务端返回三条独立队列项，并保持确认顺序。
- [ ] Web 刷新、iOS 退出再进入或后端重启后，未执行的队列项仍存在。
- [ ] 后端重启恢复完成后，未暂停且未阻塞的队列从第一条未执行消息继续自动处理；用户暂停或失败阻塞的队列保持原状态。
- [ ] 排队与执行过程不重置 ACP session，后续消息能够使用此前对话上下文。
- [ ] 已被领取的消息遇到后端重启时按“执行中断”收口，不自动作为新消息重跑；未领取消息仍可恢复。

### US-002：查看跨端一致的队列

**用户故事：** 作为同时使用 Web 和 iOS 的用户，我希望两端看到同一队列，以便明确还有哪些消息等待执行。

**验收标准：**

- [ ] 进入普通 Job 时，客户端主动读取服务端队列，不依赖当前页面的旧内存状态。
- [ ] Web 入队后，已打开同一 Job 的 iOS 能更新队列；iOS 入队后 Web 也能更新。
- [ ] 断线重连、App 回到前台和页面重新可见时，客户端重新校准服务端队列。
- [ ] 实时通知丢失时，重新读取仍能得到完整、正确的队列快照。
- [ ] 队列读取失败时不得显示成“空队列”，而是保留最近快照并显示完整同步错误。
- [ ] 当前轮结束但队列仍会继续执行时，客户端不得因为一次终态事件永久断开实时通道或短暂显示成整体空闲。

### US-003：删除尚未执行的排队消息

**用户故事：** 作为用户，我希望删除不再需要的排队消息，避免它在当前任务结束后继续执行。

**验收标准：**

- [ ] 每条等待中的队列项都有独立删除入口。
- [ ] 删除成功后，该队列项立即从所有客户端消失，且之后不会被发送给 Agent。
- [ ] 对同一队列项重复删除得到一致的成功结果，不产生额外副作用。
- [ ] 若消息已被服务端领取，删除请求明确失败并返回“已开始执行”的完整状态；用户可改用停止当前执行。
- [ ] 删除请求失败时，队列项继续显示，不做假删除，并展示完整错误。
- [ ] 删除与自动领取并发时，服务端只能产生一种结果：删除成功且永不执行，或领取成功且删除被拒绝。

### US-004：停止并暂停后续队列

**用户故事：** 作为用户，我希望停止当前生成时同时暂停后续排队消息，以免下一条立即启动造成“停止无效”的误解。

**验收标准：**

- [ ] 当前执行存在排队消息时，停止操作明确说明“停止当前消息并暂停队列”。
- [ ] 停止完成后，剩余消息继续保留但不会自动执行，Web 与 iOS 均显示“队列已暂停”。
- [ ] 用户可在任一端点击“继续队列”，服务端从当前队首恢复执行。
- [ ] 暂停期间新增消息追加到队尾，不会隐式恢复队列。
- [ ] 删除全部剩余消息后，暂停状态自动清除；此后新消息可按普通空闲 Job 立即执行。
- [ ] 后端重启后仍保留用户主动暂停状态，不得自动恢复执行。
- [ ] 当前轮自然完成或执行失败时不暂停队列，仍按顺序处理下一条。

### US-005：Web 排队区改版

**用户故事：** 作为 Web 用户，我希望排队消息整齐吸附在输入框上方，以便查看队列而不影响输入。

**验收标准：**

- [ ] 排队区位于文本输入框外部并紧贴其上边缘，与输入框组成一个整体容器。
- [ ] 一条消息占一行，多次发送显示为多行，不再使用横向标签或自动换行标签。
- [ ] 每行展示单行文本摘要；纯图片消息展示图片数量，图文消息同时展示文本摘要与图片标识。
- [ ] 长文本单行省略，悬停或聚焦时可查看完整内容，不撑高单行。
- [ ] 每行右侧提供明确的删除按钮；删除处理中只锁定当前行。
- [ ] 队列暂停时展示暂停原因和“继续队列”入口，不能仅靠颜色表达状态。
- [ ] 队列较长时列表在限定高度内滚动，不持续挤压消息区和文本输入区。
- [ ] 队列为空时不保留空白占位；出现队列时输入框宽度和发送按钮位置不跳动。
- [ ] 在桌面和窄屏浏览器中验证键盘操作、屏幕阅读器标签、删除反馈与明暗主题。

### US-006：iOS 排队区改版

**用户故事：** 作为 iOS 用户，我希望在输入框上方以紧凑列表查看和删除排队消息，并在重新进入页面后继续看到它们。

**验收标准：**

- [ ] 排队区紧贴输入框上边缘，每条排队消息独占一行。
- [ ] 队列项展示单行摘要、图片标识、等待状态和删除按钮。
- [ ] 队列较长时列表内部滚动，并适配键盘、安全区和不同尺寸 iPhone。
- [ ] 已由服务端确认排队的消息不再作为普通用户气泡重复出现在消息时间线中。
- [ ] App 切到后台再返回、退出对话再进入或重新连接后，以服务端队列恢复界面。
- [ ] 删除期间当前行显示处理中状态；失败时保留该行并可查看、复制完整错误。
- [ ] 队列暂停时展示暂停原因和“继续队列”入口。
- [ ] 在 Simulator 或真机上验证连续入队、逐条删除、后台恢复和 Web/iOS 同时操作。

## 5. 功能方案

### 5.1 服务端队列项

每条队列项至少保存以下业务信息：

- 稳定的客户端消息标识，同时作为跨请求去重标识。该标识在同一 Job 的普通消息队列、执行记录、删除记录和命令记录之间使用统一命名空间。
- 所属 Job、服务端确认顺序和创建时间。
- 提交来源与操作者标识，用于跨端展示和审计，不用于拆分队列。
- 文本、服务端图片引用，以及完整的发送上下文。
- 目标会话策略：显式指定的会话或“执行时使用最新兼容会话”。
- 入队时选定的 Agent 稳定身份与版本、模型、模式和思考等级。
- 当前状态、最近更新时间和完整失败原因。

排队消息与已经发送给 Agent 的历史消息分开保存。排队阶段不进入对话历史；被服务端领取并接受执行后，使用同一个稳定消息标识转成普通用户消息，客户端不得出现闪烁或重复气泡。

### 5.2 统一消息状态机与幂等

服务端为每个客户端消息标识维护一条持久化生命周期记录，队列和现有执行回执不能各自维护互不相干的去重状态。状态按以下方向单向变化：

- `queued → processing → completed / failed / stopped / interrupted`
- `queued → blocked → deleted`
- `queued → deleted`

其中 `queued` 和 `blocked` 出现在可见队列中；`processing` 及其终态属于当前执行和历史记录；`deleted` 不再出现在队列中，但删除标记、内容指纹和必要时间必须保留到 Job 删除，以承接迟到重试，不需要继续保留已删除消息的正文。

同一消息标识的处理规则：

- 标识第一次出现时，服务端保存完整内容摘要并进入上述状态机。
- 相同标识、相同完整发送语义的重试返回已经保存的状态，不重复入队、执行或写入用户输入审计。
- 相同标识对应不同文本、附件、目标会话或运行配置时明确拒绝。
- 已用于命令的标识不能用于普通消息，已用于普通消息的标识也不能用于命令。
- 队列项从 `queued` 转为 `processing` 时，执行回执必须同时生效；不存在“队列已移除但执行回执尚未建立”的可见中间状态。
- 服务端只有在队列项、消息生命周期、队列版本和暂停状态已经持久化后才返回成功；返回成功的排队消息不得因进程退出而丢失。
- 外部 Agent 不提供 exactly-once 保证，因此本功能采用“领取前可恢复、领取后不自动重跑”的边界。服务端在领取后崩溃时，该消息收口为 `interrupted`，由用户使用新的消息标识手动重发，避免重复产生工具副作用。

### 5.3 会话与运行配置规则

- 客户端显式指定会话时，该队列项固定使用此会话；执行前如果会话已不存在、已不属于该 Job 或与 Agent 不兼容，则进入 `blocked`，不静默切换会话。
- 客户端未显式指定会话时，队列项保存“自动选择”策略；实际执行时使用该 Job 最新且与入队 Agent 兼容的有效会话。
- 前一条消息创建了新会话时，后一条使用“自动选择”的消息应自然跟随该新会话。
- Agent 使用入队时解析出的稳定身份与版本；模型、模式和思考等级也在入队时冻结，之后客户端修改默认配置不会改写既有队列项。
- 冻结的 Agent 版本或配置在执行前失效时，该项进入 `blocked` 并展示完整原因，不自动替换 Agent、重置 session 或降级配置。

### 5.4 提交规则

客户端统一提交消息，服务端在 Job 级串行边界内作出以下决定：

1. 同一消息标识已存在时，校验完整发送内容。内容一致则返回原有状态，内容不同则拒绝并报告标识冲突。
2. Job 空闲且队列为空时，消息直接进入现有执行流程。
3. Job 正在运行或队列非空时，消息持久化到队尾，再向客户端确认“已排队”。
4. 即使 Job 在客户端提交过程中刚好结束，也必须由服务端保证该消息只会“立即执行”或“成功入队”一次。
5. 单条消息沿用现有内容与附件限制；单个 Job 最多保留 100 条未执行消息，超过上限时拒绝新消息并返回完整错误。

图片必须先完成上传并获得服务端引用，之后才能成为可跨刷新恢复的正式队列项。仍在设备本地上传的图片只属于短暂提交状态，界面必须与“服务端已排队”区分。

已识别的 Slash 命令在进入普通消息状态机之前处理，永不进入服务端消息队列：

- 只读查询类命令可立即执行。
- 导航、切换或其他有副作用的命令在当前轮运行时明确拒绝，并由客户端保留原输入供用户稍后重试。
- 未识别的 Slash 文本继续按普通用户消息处理；带附件或明确要求绕过命令解析的内容也按普通消息处理。

### 5.5 服务端调度职责

服务端提供统一的消息编排能力，立即发送与后台队列发送必须经过同一套参数校验、会话选择、Agent 准备、标题处理、审计记录和执行逻辑。HTTP 请求只负责提交意图，不持有队列后续执行责任。

每个 Job 同一时刻只能有一个队列调度过程。以下情况都会唤醒同一个调度入口：

- 新消息提交后发现 Job 可以立即执行。
- 当前轮自然完成或执行失败，且旧运行已经完全退出。
- 用户显式继续一个暂停队列。
- 阻塞队首被删除。
- 服务启动完成当前执行中断修复后。

调度器在领取下一条之前，必须确认上一轮执行协程已经退出，停止句柄、完成通知和 Agent 执行占用等运行资源已经释放。随后在 Job 级串行边界内完成可执行性校验，并将队首从 `queued` 原子转为 `processing`，再启动新一轮。不能仅以 Job 已写入终态或已经发布终态事件作为领取条件。

### 5.6 自动执行与暂停规则

- 当前轮自然完成或执行失败后，服务端在旧运行完全退出时自动处理队首。执行失败不清空剩余队列。
- 用户主动停止当前执行时，服务端先无条件建立持久化暂停屏障，再停止当前轮；停止与同期入队按同一个 Job 级顺序处理，避免新消息落在暂停屏障之外。
- 用户显式继续后，服务端清除暂停状态并从队首恢复。暂停期间新增消息只追加到队尾，不会隐式继续。
- 如果队首为 `blocked`，继续请求明确失败并返回该项的完整错误；用户删除阻塞项后，队列自动继续。
- 当前轮完全停止后，如果队列为空，暂停状态自动清除；暂停后所有消息都被删除时也自动清除。之后主动发送的新消息可以正常立即执行。
- 系统进程退出、崩溃或重启造成的执行中断不视为用户主动暂停。服务端先将已领取的消息收口为 `interrupted`，不重复执行它，再继续处理尚未领取的队列。
- 每次只领取一条；该消息完成执行前，其他项始终留在队列中。
- 服务端在队首仍可删除时完成会话、Agent 和运行配置校验。确定无法通过的配置错误会将该项改为 `blocked`，保存完整原因并暂停后续队列；校验通过后才原子转为不可删除的 `processing`。
- 临时资源不足、短暂存储失败等可恢复错误不得把消息标记为已执行或丢出队列；队列保留原顺序，以有上限的退避策略重试，并向客户端暴露完整错误。持久化 `processing` 状态失败时绝不能启动 Agent。
- 阻塞队列的失败项被删除后，服务端自动继续处理下一条，不需要客户端额外触发。
- 服务启动时先修复被中断的当前执行，再恢复每个普通 Job 的未执行队列；已被确认删除或已经执行的标识不得重新入队。

### 5.7 删除规则

- 只有“等待中”和“等待处理失败”的队列项可删除。
- 服务端在同一 Job 的串行边界内完成“确认仍可删除”和“持久化删除”，然后才返回成功。
- 已进入领取或执行阶段的消息不可删除，避免接口显示成功但 Agent 仍收到消息。
- 删除结果持久化保留去重语义。客户端因超时重试原提交请求时，服务端返回“已删除”，不得重新创建队列项；用户重新发送相同内容时必须使用新的消息标识。
- 删除 Job 时，其未执行队列随 Job 数据一起清理。

### 5.8 用户输入审计与附件生命周期

- 普通消息在服务端首次持久化接纳时写入一次用户输入审计：立即执行消息在执行接纳时写入，排队消息在入队成功时写入。重试不得重复记录。
- 用户之后删除排队消息时保留审计记录，因为该记录表达的是“系统曾正式接纳该输入”；排队消息仍不会进入 Agent 对话历史。
- 审计写入继续沿用现有的非阻塞容错原则；审计失败必须记录完整错误，但不能把已经持久化成功的队列项回滚或重复执行。
- 已入队图片的服务端引用至少保留到队列项进入执行历史或 Job 被删除。删除单个队列项时不立即删除图片文件，避免破坏其他消息对同一文件的引用。
- 本期沿用现有上传文件的持久化策略，不新增孤立上传文件回收；统一的未引用上传清理机制作为后续独立能力。

### 5.9 查询与实时同步

服务端提供以下能力：

- 提交消息，并返回“立即执行”“已经排队”“重复请求”或“已经删除”等明确状态，以及该消息的当前生命周期状态。
- 按服务端顺序读取某个 Job 的完整待处理队列。
- 按稳定消息标识删除单条队列项。
- 当前执行停止时原子建立队列暂停状态；用户可以显式继续队列，并获得最新队列版本。
- 在入队、删除、领取、失败或恢复时，通过现有 Job 实时通道发送队列变化通知。

实时通知只用于提醒客户端刷新，不替代持久化快照。队列快照包含递增版本、是否暂停和暂停原因；客户端只应用更新版本，避免并发请求的迟到响应把新队列覆盖成旧状态。

客户端收到单轮终态后先收口当前消息，再依据权威 Job 与队列状态决定连接生命周期。当队列仍有可执行消息或服务端正在进行轮次交接时，客户端必须保持或恢复现有 Job 实时订阅，不能因为一次 `JOB_COMPLETED`、`JOB_FAILED` 或 `JOB_STOPPED` 就永久断开。只有服务端确认当前无执行、无待自动执行消息且不处于交接状态时，客户端才进入真正空闲态。

### 5.10 Web 交互

- 移除页面内存队列的业务权威性；本地状态只负责提交中、上传中和结果未知的短暂反馈。
- 进入 Job、实时重连和页面重新可见时读取服务端队列；收到队列变化通知后重新校准。
- 排队面板与输入框共用外轮廓，位于编辑区正上方；面板底边与输入框顶边无间隙。
- 每行从左到右展示队列顺序、内容摘要、附件提示和删除按钮。
- 队列暂停时在面板顶部展示原因和“继续队列”按钮；等待处理失败时在对应行提供完整错误入口。
- 服务端领取队首消息后，该行平滑移出排队面板，并以相同消息标识进入对话时间线。
- 提交结果未知时保留临时行并使用原消息标识查询或重试；不得生成第二条排队消息。
- 单轮终态后若队列即将继续，保持运行态和实时连接，不闪回可立即发送的空闲样式。

### 5.11 iOS 交互

- 将当前页面内存 outbox 的“等待发送”部分迁移为服务端队列；上传中、提交中和结果未知仍可保留为短暂本地状态。
- 服务端已排队项只显示在输入框上方的队列面板，不同时显示在对话时间线。
- 队列行采用适合单手操作的删除热区，并支持系统无障碍标签；是否增加滑动删除可在实现时作为同一删除动作的快捷入口。
- 队列暂停时在面板顶部展示原因和“继续队列”按钮；等待处理失败时可查看和复制完整错误。
- App 回到前台时先校准 Job、历史消息和队列，再决定是否继续实时订阅。
- Web 与 iOS 同时删除或发送时，均以服务端返回和最新队列版本收敛，不依赖本地推测。
- 单轮终态后若队列即将继续，保持运行态和实时连接，不闪回可立即发送的空闲样式。

## 6. 状态与边界语义

| 状态 | 用户可见含义 | 是否可删除 | 后续行为 |
| --- | --- | --- | --- |
| 提交中 | 客户端尚未确认服务端是否接收 | 否 | 使用同一消息标识查询或重试 |
| 等待中 | 已由服务端持久化，等待前序消息结束 | 是 | 队列未暂停时按服务端顺序自动执行 |
| 等待处理失败 | 服务端领取前校验失败，完整原因已保存 | 是 | 暂停该 Job 后续队列 |
| 已领取/执行中 | 已从队列转为当前轮次 | 否 | 使用现有停止能力控制 |
| 已删除 | 已持久化取消，不再执行 | 不适用 | 同标识重试仍返回已删除 |

队列是否暂停是 Job 级持久化状态，不是某条消息的生命周期状态。用户主动停止和执行前确定性校验失败都可以让队列暂停，但必须记录不同的暂停原因；前者可直接继续，后者需要先删除阻塞项，本期不提供原地重试。

以下竞态必须有确定结果：

- **提交与当前轮结束并发**：消息只执行一次，且不会滞留在一个无人触发的队列中。
- **删除与领取并发**：只有一个动作成功，不允许“删除成功后仍执行”。
- **两个客户端同时提交**：以服务端确认顺序为准，不按设备时钟排序。
- **断线后重试**：相同消息标识和内容返回原状态；相同标识但内容不同明确冲突。
- **后端重启**：未领取项保留；中断中的当前消息沿用现有中断恢复语义，不把它重新当作新队列项执行。
- **停止与入队并发**：按服务端 Job 级顺序收敛；停止建立的暂停屏障覆盖仍未开始执行的新队列项。
- **终态与下一轮交接**：上一轮终态先持久化并发布，运行资源完全释放后再领取下一条；客户端通过快照校准覆盖两轮间的通知窗口。

## 7. 权限与错误处理

- 查看队列沿用 Job 查看权限；提交和删除沿用 Job 执行权限。
- 当前部署模型不做用户级队列隔离：有相应权限的用户可以查看和删除该 Job 的共享排队项。
- 提交时完成权限校验；一条消息被服务端持久化接纳后，后续后台执行不依赖原客户端 Cookie 是否仍有效。权限变化不追溯取消已经接纳的消息，具备执行权限的用户仍可删除尚未领取的队列项。
- Job 不存在、已删除、模式不支持、队列已满、消息标识冲突、队列项已领取、附件无效和持久化失败均返回可区分的错误。
- Web 与 iOS 可以先展示简短摘要，但必须提供完整错误详情与复制能力。

## 8. 非目标

- 不支持 Graph Job 或历史 Loop Job 的消息排队。
- 不支持拖拽调整顺序、插队、批量删除或跨 Job 移动队列项。
- 不把未上传完成的本地附件视为服务端已排队。
- 不通过删除队列项停止已经开始的 Agent 执行。
- 不因 ACP 工具并发错误、队列切换或消息失败重置 session。
- 本期不把 Slash 命令纳入服务端消息队列；运行中的只读查询命令可以立即执行，导航、切换和其他有副作用的命令由服务端明确拒绝并提示稍后重试。
- 不在本功能中增加未引用上传文件的垃圾回收机制。

## 9. 实施顺序

1. 定义统一消息生命周期、队列项、暂停状态、队列版本和提交结果语义。
2. 把消息参数校验、会话选择、Agent 准备、标题处理、审计记录和执行收敛为服务端统一编排能力。
3. 完成 Job 级持久化、原子入队/领取/删除、运行资源完整交接、启动恢复和自动串行执行。
4. 补齐队列读取、删除、继续和实时变化通知，并接入现有权限。
5. 调整 Web 与 iOS 的终态和 SSE 生命周期，确保连续队列执行不会漏事件或闪回空闲。
6. Web 改为服务端队列并完成吸附式逐行列表。
7. iOS 改为服务端队列并完成输入框上方的逐行列表。
8. 完成单端刷新、后端重启、Web/iOS 跨端和关键竞态验收。

## 10. 验收场景

- [ ] 运行中从 Web 连续发送三条消息，刷新页面后三条仍按原顺序显示并依次执行。
- [ ] 运行中从 iOS 发送两条消息，杀掉 App 后重新进入，两条仍存在。
- [ ] Web 与 iOS 同时打开同一 Job，在一端新增或删除队列项，另一端最终显示一致。
- [ ] 删除队首时与当前轮结束同时发生，最终只出现“成功删除”或“已开始执行”之一。
- [ ] 提交响应丢失后用相同消息标识重试，不产生重复队列项或重复 Agent 执行。
- [ ] 队列项从等待转为执行时，其队列状态和执行回执原子切换，不存在可被重试再次入队的间隙。
- [ ] 后端存在未执行队列时重启，未暂停队列在修复中断状态后继续执行；用户暂停和失败阻塞的队列保持暂停；已完成或中断消息不重复。
- [ ] 当前轮自然完成或执行失败后，剩余队列继续按顺序处理。
- [ ] 用户主动停止当前轮后，剩余队列保持暂停；新增消息只追加，点击“继续队列”后才从队首执行。
- [ ] 用户停止当前轮时恰好有新消息入队，最终该消息必须受暂停状态约束，不会意外启动。
- [ ] 上一轮终态到下一轮开始之间，服务端确认旧运行资源已完全释放，两端不会漏掉下一轮开始事件或闪回空闲状态。
- [ ] 队列项执行前发现配置失效时，队列暂停在失败项，完整错误在 Web 与 iOS 均可查看和复制。
- [ ] 显式指定的 session 失效时消息进入阻塞状态；未指定 session 的消息跟随前一条创建的最新兼容 session。
- [ ] 入队后修改默认 Agent、模型、模式或思考等级，不改变既有队列项冻结的运行配置。
- [ ] 同一消息标识先用于命令再用于普通消息，或反向复用时，服务端明确拒绝。
- [ ] 已删除队列项的原提交响应丢失后重试，服务端仍返回已删除且不会重新入队。
- [ ] 服务端在领取后、Agent 结果确认前重启时，该消息显示为中断且不自动重跑；用户可用新消息标识手动重发。
- [ ] 排队消息只写入一次用户输入审计；删除后保留审计，但不进入 Agent 对话历史。
- [ ] Web 队列每条一行、吸附在输入框上边缘；长队列内部滚动，文本输入区域不被占用。
- [ ] iOS 队列每条一行、吸附在输入框上边缘；键盘弹出、后台恢复和不同屏幕尺寸下均可操作删除。
- [ ] 普通消息进入执行后只出现一个用户消息气泡，队列行与历史消息之间无重复。
- [ ] 整个流程未重置 ACP session，后续消息能够引用前序上下文。

## 11. 成功标准

- 已被服务端确认排队的消息在刷新、重进页面和后端重启场景下丢失率为 0。
- 同一客户端消息标识触发重复 Agent 执行的次数为 0。
- 删除成功后仍被执行的次数为 0。
- 用户主动停止后，在显式继续前启动后续队列项的次数为 0。
- 连续两轮交接期间因客户端主动断开而漏掉新一轮开始状态的次数为 0。
- Web 与 iOS 在重新同步后，队列内容、顺序和状态与服务端一致。
