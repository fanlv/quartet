# SSE 断开后历史 Job 发消息重复显示旧回复

日期：2026-06-03

## 现象

在 SSE 已断开的情况下（典型是服务重启后、或页面长时间空闲后），进入一个历史 Job 发送消息，回复正常，但发送后会**立刻多显示一条之前已经出现过的旧回复**。被重复显示的内容形如：

```
[No content][No content][No content]襄阳今明两天天气如下……
```

刷新页面后这条重复消息依然存在（说明它已经被写进了磁盘历史，不是纯前端渲染问题）。

## 根因

这是后端层面的问题，与前端去重无关。

ACP 子进程（外部 Agent CLI）在新一轮 Run 开始、需要重新对齐会话上下文时（服务重启 / 长时间空闲后子进程被重建或重新加载会话），会把它会话记忆里**上一轮的 assistant 回复重新输出一遍**（回放 / echo）。这条回放消息有两个明显特征：

1. 内容以占位符 `[No content]` 开头（子进程把空内容块渲染成了字面量 `[No content]`，该字面量完全来自子进程，后端代码中不存在）；
2. 落盘时 `started_at == finished_at`（瞬时产生，没有真实的流式生成过程）。

后端的轮次构建逻辑把这条回放消息当成了本轮新产生的 assistant 消息：

- 给它分配了一个**全新的消息 ID**；
- 写入磁盘历史；
- 通过 SSE 推送给前端。

前端所有的消息去重都是按**消息 ID** 进行的。由于这条回放消息的 ID 是全新的，与历史里那条原始回复的 ID 不同，前端无法识别为重复，于是立刻多渲染了一条旧内容。磁盘历史里也因此多出一条重复消息。

### 为什么只在 SSE 断开 / 重启后出现

正常在线连续对话时，子进程会话内存是连续的，不需要回放上一轮内容；只有当服务重启、或长时间空闲导致子进程被重建 / 重新加载会话时，新一轮 Run 才会触发这次回放，从而暴露问题。

### 与"消息消失"是两个独立问题

本仓库此前修复的"SSE 断开后发消息、消息消失"问题，原因是前端断线恢复路径用覆盖式写入丢弃了未确认的乐观消息（已修复）。本问题正相反——是**多**出一条旧消息，根因在后端把子进程的历史回放当成了新消息落盘并转发。两者互相独立。

## 解决方案

在后端落盘前识别并丢弃这种"子进程历史回放"消息：当一条 assistant 消息呈现出回放特征（内容以 `[No content]` 占位符开头、且为瞬时产生）时，判定它是对已有历史的重复输出，**不写入磁盘历史**，从源头阻止重复消息进入历史。

判定采用双信号叠加，避免误伤合法的短回复：

- 内容以回放占位符 `[No content]` 开头（该字面量完全来自子进程，正常流式回复绝不会有）；
- 消息为瞬时产生（结束与开始时间差在极小阈值内），区别于真实流式回复的数百毫秒到秒级耗时。

落盘拦截解决了核心问题——磁盘历史不再被污染、刷新后不再出现重复、历史重载也不再带出重复消息。子进程实时流式发出 echo 的那一瞬，前端可能仍会短暂闪现一次（随下一轮覆盖消失），作为已知的次要瑕疵接受。

## 影响范围

- 仅 ACP 路径的落盘逻辑，不影响正常的流式回复，也不影响 eino 路径。
- 正常 assistant 回复不带 `[No content]` 前缀、且耗时远超阈值，不会被误判。
- 覆盖触发场景：服务重启后、或长时间空闲后，在历史 Job 继续发消息。
