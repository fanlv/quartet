# 历史 / 长时间无响应 Job 发消息后消息不显示

日期：2026-06-03

## 现象

在以下两种场景里发消息，用户的消息发送后**不会出现在消息列表里**，必须手动刷新页面才能看到：

1. 在一个长时间没有回复（空闲很久）的 Job 页面发送消息。
2. 服务重启后，进入一个历史 Job 继续追问。

刷新页面后消息正常出现，说明后端最终已经把消息落盘，问题只发生在前端运行态的消息列表上。

## 根因

这两个场景的共同点是：发消息时，前端与后端之间的 SSE 连接其实已经失效——要么是页面空闲太久、服务端把该连接的续传点（resume point）回收了，要么是服务重启后旧的续传点在新进程的缓冲区里不存在。

正常发消息的流程是：

1. 前端先把用户消息以"乐观消息"的形式插入消息列表（带一个本地生成的 `clientMessageId`，标记为待确认）。此时消息其实已经显示出来了。
2. 由于检测到 SSE 已断开，前端触发 SSE 重连。
3. 随后到来的 `RUN_STARTED` 事件会凭 `clientMessageId` 把这条乐观消息"转正"（确认）。

问题出在第 2 步的重连过程。当旧的续传点在服务端已不存在时，SSE 重连会收到"续传点已失效"的响应，进而走**断线恢复路径**。这条恢复路径会直接从磁盘重新加载该 Job 的全部历史消息，并用历史消息**整体覆盖**当前的消息列表。

而此刻这条刚发出的乐观消息：

- 还没被 `RUN_STARTED` 事件确认；
- 也还没（或刚刚才）被后端落盘，磁盘历史里大概率读不到它。

于是它在这次整体覆盖中被直接丢弃，UI 上就消失了。等到刷新页面时，后端早已落盘完成，历史里能读到这条消息，它便重新出现——与现象完全吻合。

## 为什么已有的修复没生效

代码里已经有一处针对"重新加载历史时不要误删未确认的乐观消息"的修复，但那处修复作用在**消息合并**逻辑上：合并时会保留历史中不存在、但本地尚未确认的乐观消息。

然而断线恢复路径并不走合并逻辑，而是直接整体**覆盖**消息列表，因此完全绕过了那处修复。修复打在了相邻、但不是真正触发问题的那条路径上。

## 解决方案

让断线恢复路径在重新加载磁盘历史后，**复用同一套消息合并逻辑**，而不是整体覆盖消息列表。

合并逻辑已经能够：

- 按消息 ID / 工具调用 ID 正确地用历史版本替换运行态版本（这正是覆盖式写入想达到的目的）；
- 同时保留历史中尚不存在、且本地尚未确认（`clientMessageId` 未出现在历史中）的乐观用户消息。

这样一来，刚发出的消息会被保留在列表里，等后续 `RUN_STARTED` 事件凭 `clientMessageId` 将其确认转正；磁盘历史里已有的消息也能被正确 reconcile，不会产生重复。

## 影响范围

- 仅前端运行态消息列表的处理逻辑，不涉及后端协议与落盘格式。
- 覆盖两种触发场景：长时间空闲后发消息、服务重启后在历史 Job 继续追问。
