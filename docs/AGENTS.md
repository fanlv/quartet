## 目录说明

### docs 文档规范

* 文件名是如果是 feature 应该是 feature-YYYY-MM-DD-xxx.md , 比如 feature-2026-05-03-user-input-logging.md，依次类推。
* 多文件方案允许用同名子目录组织：目录命名沿用 `feature-YYYY-MM-DD-xxx/`，子目录内的文件可用 `<编号>-<小标题>.md`（如 `00-overview.md` / `01-architecture.md`）做内部排序，无需重复日期前缀。
* 方案文档里面不要有代码细节，是功能的描述文。
* 文档在不丢失细节的情况下，尽量保持简洁，不要长篇大论。


技术方案应该包含（但不限于）以下内容：

```
# 技术方案：xxx

## 背景（必须要写）
当前现状是什么
具体痛点 / bug / 业务诉求是什么
为什么现在要做
不解决会有什么影响

## 目标 （必须要写）
要解决什么问题。

## 范围 （可选）
做什么，不做什么。

## 方案设计（必须要写）
准备怎么实现。

## 风险（可选）
可能有什么问题，怎么规避。没有风险可以不写。

## 可观测性
日志

## 执行步骤 （必须要写）
把需求拆成多个小步骤，每个步骤都有明确的职责。

## 验收标准（必须要写）
* 列出所有功能列表。
* 标记功能是需要 E2E 测试还是单测
* 标明需要用户手工测试的功能。

```
